## 一切的起点：模型编了一套不存在的积分规则

我做了个假知识库，叫「星尘咖啡」，里面写着会员积分规则。然后直接问模型：

> 星尘咖啡的会员积分规则是什么？

它答得又快又顺，分几档、多少分兑什么、有效期多久，条理清晰，**全套都是编的**。知识库里一个字都没有。

把 RAG 链接上之后同样的问题，它开始一字一句有出处。再问一个知识库里确实没有的「你们股票代码多少」，它回「资料中未提及」。

这一下把 RAG 的本质说完了：**模型不是知识源，是语言引擎。知识得我们递给它，还得教它在没资料时闭嘴。**

然后我踩了整整两周的坑，都在「递得对不对」这件事上。

## 第一条经验：先分清是检索错还是生成错

这是我最想提前知道的一条。

答案质量差，人的本能是去改提示词、换模型。但 RAG 的答案由两段决定：**检回来什么**，和**拿检回来的东西怎么生成**。这两段的修法完全相反，搞错了就是白折腾。

所以任何一次调优，第一步都不是看答案，是把检索的中间结果单独打印出来看：

```python
docs = retriever.invoke(question)
for d in docs:
    print(d.metadata['source'], '·', d.page_content[:60])
```

检回来的东西就不对，那在检索端调，改提示词一点用没有；检回来的明明有答案，模型却没用，那才轮到生成端和提示词。

**回答不好先分清是检索错还是生成错**，这句话听起来像废话，但我在没打印中间结果之前，白改过好几轮提示词。

## 第零层：文档怎么切

Embedding 把文本压成向量，向量检索找的是「语义最近的块」。切得不好，语义就被切断了。

```python
RecursiveCharacterTextSplitter(
    chunk_size=300, chunk_overlap=50,
    separators=['\n\n', '\n', '。', '！', '？', '，', ' ', ''],
)
```

`chunk_size=100` 且不留重叠，能把「近似最近邻搜索」这个词组从中间劈成两半，两边各自都不再表达这个概念。

中文有个额外的坑：**`chunk_size` 数的是字符数，不是 token**。同样 300，英文能装下五六个词，中文只装得下一百来个字。所以中文库的 chunk_size 一般要比英文经验值往上调。

选型上没有标准答案，只有区间：技术文档 300~800，法律条款 500~1000，对话记录 200~400；`chunk_overlap` 取 chunk_size 的 10%~20%。

还有一个字母之差能毁掉整个引用功能：

```python
chunks = splitter.split_documents(docs)   # 对，metadata 跟着走
chunks = splitter.split_text(text)        # 错，metadata 全丢
```

用 `split_text`，切出来的块是纯字符串，来源文件、页码、标题统统没了。后面想做「点击查看原文出处」，直接死在这一步。

## 第一层：查询侧，用户不会按你的文档措辞提问

真实的失败长这样：

| 用户怎么问 | 知识库里怎么写 | 病因 |
|---|---|---|
| 你们家买一送一吗？ | 500 分可兑换任意中杯饮品一杯 | 用词不同，向量不近 |
| 加班到晚上还能喝到吗？ | 工作日 8:00-22:00 | 问法隐晦，语义绕了一圈 |
| 积分咋整？生日有优惠吗？ | 分别在两个不同文档块 | 口语 + 一次问了两件事 |

三招对应三种病因：

**MultiQuery** —— 让 LLM 把原问题改写成几个不同角度的变体，各自检索，取并集去重。「买一送一」会被改写成「优惠活动」「促销活动」「会员有什么饮品折扣」，于是命中那条从没写过「买一送一」的积分规则。代价很实在：**3 倍检索 + 1 次 LLM 调用**。

**查询分解** —— 把复合问题拆成子问题分别查。要在提示词里限死「最多 3 个」，不限数量它能给你拆出十个。

**HyDE** —— 反过来：先让模型就着问题**编一段假设性答案**，拿这段假答案去检索。因为假答案是按文档的口吻写的，和真文档在向量空间里比口语问题更接近。

HyDE 有个必须记住的禁区：**含专有名词、型号、编号的查询不要用**。它会把「Hario V60」一本正经地扩写成一段关于手冲壶的泛泛描述，然后检索到一堆无关文档。

## 第二层：向量搞不定的精确词，交给 BM25

这是我这轮最大的认知修正。

| 查询 | 向量检索的表现 |
|---|---|
| Milvus 2.6 的全文检索怎么配 | 2.4 和 2.6 的文档语义几乎一样，分不出 |
| 错误码 E1002 | 编号几乎无法语义化，约等于抓瞎 |
| 手冲壶 Hario V60 | 型号词被当成噪声 |

**专有名词、型号、编号这类词，在 embedding 里经常被「平均」掉。** 而 BM25 统计词频和逆文档频率，正好专治这个。语义靠向量，精确靠 BM25，两者是互补不是替代。

难点在于两路各出一个榜单，向量的 0.9 分和 BM25 的 21.3 分根本没法相加。RRF（倒数排名融合）的解法很聪明——**只看名次不看分数**：

```
score(doc) = Σ 1 / (k + rank_i(doc))      # k 常用 60
```

一个文档在两路都靠前，综合分就高。Milvus 原生支持，建表时多写三行：

```python
schema.add_field('text', DataType.VARCHAR, max_length=1000,
                 enable_analyzer=True, analyzer_params={'type': 'jieba'})
schema.add_field('sparse', DataType.SPARSE_FLOAT_VECTOR)
schema.add_function(Function(name='bm25_func', function_type=FunctionType.BM25,
                             input_field_names=['text'], output_field_names=['sparse']))
```

意思是：**你只管写文本，BM25 稀疏向量由数据库自己算。**

跑完三组对照，结果非常干净：纯向量把 2.4 和 2.6 混在一起；纯 BM25 精确锁定 2.6；RRF 融合取长补短。

两个坑我撞过：`AnnSearchRequest` 必须传对象，传 dict 会报 `'dict' object has no attribute 'data'`；分词器在 **Milvus Lite 上只认 `jieba`**，写 `chinese` 直接 `unknown tokenizer type`，那是 Docker Standalone 2.6 才有的选项。

## 第三层：宽召回 + 精排序

初检用的 embedding 模型是「快但糙」。所以别指望它一次就把最相关的排到第一，改成两段式：

```
先多拿一些（k=10~20）→ 换个更贵的模型重新精排 → 只把 Top-3 喂给生成
```

精排可以用 LLM 逐个打分，但有两个工程真相书上不讲：

```python
try:
    score = int((prompt | model).invoke({}).content.strip())
except ValueError:
    score = 0          # 模型会输出「8 分」「相关度 9」，必须兜底
```

一是 **LLM 不老实遵守「只输出一个整数」**，`int()` 会崩；二是这个循环是**串行调用**，文档一多就慢得没法用。这才是生产上真正要换交叉编码器（bge-reranker 这类，一次前向算完所有分数）的理由，而不是「精度更高」那句空话。

上下文窗口寸土寸金，**宁可少给、给准**。

## 第四层：知识怎么存

**元数据过滤**解决的是「查错范围」。三产品线共存、只查 2025 年、多租户隔离——「咖啡味奶茶」和「咖啡」语义极近，不加过滤必然混进来。多租户场景下这不是优化，是**防止串数据的安全刚需**。

```python
retriever.invoke(question, search_kwargs={
    'k': 4, 'expr': 'category == "咖啡" and year == 2025'})
```

这里有个反直觉的 API 变化：开了 `enable_dynamic_field=True` 之后，元数据字段是**顶级字段**，写 `category == "咖啡"` 才对。网上大量老教程写的 `metadata["category"]` 在新版本直接报错，我第一次就卡在这。

**父子文档检索**解决的是「切多细」的两难：小块（200 字）语义集中、检索准，但太碎；大块（1000 字）信息完整，但 embedding 被稀释、检索不准。

解法是拆开这两件事：**用小块去检索，用大块去生成**。

```python
ParentDocumentRetriever(
    vectorstore=vs, docstore=InMemoryStore(),
    child_splitter=小切分, parent_splitter=大切分)
```

同一个问题「积分什么时候会清零？」，普通小 chunk 只回半句「过期自动清零」，必然答得支离破碎；父文档检索返回 150 多字的完整段落，里面「积 1 分」和「12 个月」都在，模型就能给出「获得之日起 12 个月」。

注意 `InMemoryStore` 重启即丢，生产要换 `LocalFileStore` 或 Redis。

## 最后：拿数字说话

上面每一招都有代价——MultiQuery 三倍检索、过滤每篇文档一次 LLM、rerank 一轮串行调用。**凭感觉叠 buff 是最贵的做法。**

RAGAS 给了四个指标，0 到 1：

| 指标 | 衡量什么 | 需要哪些输入 |
|---|---|---|
| Faithfulness 忠实性 | 答案每句话在检索资料里有没有依据（**测幻觉**） | 问题 + 答案 + 上下文 |
| Answer Relevancy 答案相关性 | 答没答到点上 | 问题 + 答案 |
| Context Precision 上下文精确率 | 检回的资料里无关的占多少（宁缺毋滥） | 问题 + 上下文 + 参考答案 |
| Context Recall 上下文召回率 | 参考答案所需信息找全没有（宁滥毋缺） | 问题 + 上下文 + 参考答案 |

算 Faithfulness 的方式很直白：把答案拆成陈述句，逐句问评委「这句在资料里找得到吗」，YES 数除以总数。所以「500 积分可兑换中杯，而且咖啡很好喝」这种前半有依据、后半是常识的句子，得分就是 1/2 = 0.5。

**关键在于后两个指标是一对跷跷板**：召回率高了精确率往往掉。诊断方向也因此很明确——

- 召回低 → 检索漏了：换 embedding、加 MultiQuery、调大 k
- 精确低 → 检索太杂：加过滤、上 rerank、调小 k
- 忠实低 → 模型在编：强化「没有就说不知道」
- 相关低 → 答跑题了：约束提示词

搭实验台时两条原则最值得记住：

**一次只改一个变量。** A 和 B 比 k，B 和 C 比 MultiQuery，同时改两个等于没测。

**评估的输入必须来自真实跑出来的结果，不是手填。** 手填测的是你想象里的系统。

## 我停在哪

诚实交代：这套东西我停在「知道怎么量」，没有一条真实的分数曲线。

本机跑的是 Ollama 的 `qwen2.5:7b` 加 `nomic-embed-text`，全程零成本零 key；LangSmith 的 API Key 我到现在都没填，`.env` 里 `LANGSMITH_TRACING` 还挂在 `false`。RAGAS 那套样本构造和 `evaluate()` 调用我照着写过，但**评估 100 条样本意味着数百次 LLM 调用**，本地 7b 跑这个不现实。

另外原计划里 Day 39 要用的 `LLMChainFilter`，我在实现时直接删掉了——本地 7b 会把明明相关的文档判成 NO，过滤完召回归零。最后退化成纯向量检索加提示词兜底。**设计文档写得很漂亮，模型能力不够就是不够。**

## 收束

如果只留一张表：

| 症状 | 该动哪一层 |
|---|---|
| 用户措辞和文档差很远 | MultiQuery / 查询分解 |
| 型号、编号、版本号查不到 | BM25 混合检索 + RRF |
| 检回来一堆但没一篇有用 | 元数据过滤 / Rerank |
| 答案有出处但只答半句 | 父子文档检索 |
| 答案漂亮但全是编的 | 提示词诚实边界 + 查 Faithfulness |
| 说不清有没有变好 | 先建评估集，再谈优化 |

四层里最容易被跳过、又最不该跳过的，是最后一层。**没有评估集的 RAG 优化，本质上是在猜。**
