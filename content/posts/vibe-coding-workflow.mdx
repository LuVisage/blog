## 「不碰键盘」是个误会

2025 年 2 月，Andrej Karpathy 给这种写法起了名字：全靠提示词，看着 AI 生成，几乎不亲自看 diff——他管这叫 vibe coding，还特意补了一句，这适合周末玩玩的小项目，不适合正经工程。

两年过去，这个词活了下来，但它的含义已经被用歪了。今天说 Vibe Coding，真正可持续的版本其实是：

> **AI 负责打字，你负责规格、验收和架构。**

差别就在最后半句。Karpathy 描述的那种「不看代码」我试过，结局都一样：生成的时候很爽，两周之后代码库变成一滩你说不清为什么能跑的泥。而我后来稳定产出的方式，恰恰是每一步都看——只是看的从「每一行怎么写」换成了「每一层对不对」。

这篇是可以跟着做的教程：从装工具、写规则文件，到一套五步工作流（提示词给全文），再到调试、重构两个专题模板和八条踩坑实录。工具怎么选看下一篇横评，这篇假设你手里有一个 agent，从零也只差十分钟。

---

## 第 0 步：把 agent 装起来

以两款终端形态为例（形态对比见下一篇）。

**Claude Code**（npm 安装，Node 18 以上）：

```bash
npm install -g @anthropic-ai/claude-code
cd 你的项目目录
claude          # 首次启动走浏览器登录授权
```

**OpenCode**（开源，引擎自带 Key）：

```bash
curl -fsSL https://opencode.ai/install | bash
cd 你的项目目录
opencode        # 首次启动选择模型，填 API Key
```

首次运行先做三件事，别急着提需求：

```text
1. 问它：「这个仓库的结构是什么？入口在哪？」——检验它读代码的能力，
   也检验它是不是真的在工作目录里；
2. 问它：「如果我让你改代码，你会怎么验证自己的改动？」——听它说测试和构建；
3. 随手丢一个只读任务：「找出所有 console.log 并列出来」——看它找得全不全。
```

三件事都过关，这个 agent 才值得交出写权限。装好后第一件事不是提需求，是写规则文件——下一节。

## 第 1 步：规则文件——把「你希望它是什么样的人」写下来

每个像样的 agent 都支持项目级规则文件：Claude Code 读 `CLAUDE.md`，各家 IDE 有各自的规则目录，而越来越多的工具直接认社区的通用约定 `AGENTS.md`。**写一次，所有会话生效**，这是整个 Vibe Coding 里性价比最高的一步。

下面是我实际在用的版本（以博客仓库为原型，可直接抄改）。注意它的结构：每一段都在回答 agent 最容易犯错的一类问题。

```markdown
# 项目约定

## 项目是什么
- 一个 Next.js 15（App Router，output: export 静态导出）+ React 19 的个人博客，
  部署在 GitHub Pages，构建产物在 out/
- 内容用 MDX 写在 content/posts，课程快照在 content/curriculum

## 命令（完成任何改动的验收标准）
- 类型检查：npx tsc --noEmit，退出码必须是 0
- 构建：npm run build，必须完整通过
- emoji 检查：node scripts/check-emoji.mjs，内容文件里不允许出现 emoji

## 硬性约束
- 不新增 npm 依赖；确需新增，先停下说明理由等我确认
- 不改动 .github/workflows/ 与部署相关配置；需要时只出方案不动手
- 不改动 scripts/import-tutorials.mjs 的输出格式
- MDX 正文里不使用裸的美元符号、花括号和尖括号

## 代码风格
- 注释只写「为什么」，不复述「做了什么」
- 优先修改现有文件；需要新建文件时先说明放哪、为什么
- 样式用现有的 CSS 变量（var(--accent) 等），不引入新样式体系

## 沟通方式
- 方案先行：超过两个文件的改动，先给方案等我确认再写码
- 每次完成任务，列出「改了哪些文件 + 验证结果」
- 不确定的事直接问，不要猜
```

五个段落各管一件事：**项目是什么**（防止它按通用模板瞎猜）、**验收命令**（把「完成」定义成可执行的命令，这是全部规则的灵魂）、**硬性约束**（依赖、部署、格式三类事故高发区）、**风格**（减少 diff 噪音）、**沟通方式**（方案先行 + 交付清单）。

写作要点：

- **规则要「可验证」**。「代码要干净」是废话，「退出码必须是 0」是规则。凡是能变成命令的验收，都写成命令。
- **禁区比要求更重要**。agent 的默认性格是热情过度，你不写「不许动部署配置」，它连 CI 都敢顺手优化。
- **控制在五十行以内**。规则文件越长，单条权重越低。塞不下的约定，放代码注释和 README。

## 第 2 步：Git 安全网——放开手脚的前提

agent 会错，而且错得理直气壮。唯一能让你放心 vibe 的保障是**任何时刻都能一键回到上一个好状态**。三个习惯：

```bash
# 1. 一个任务一个分支，别在 main 上让 agent 直接跑
git switch -c feat/reading-progress

# 2. 每完成一个可验证的小步就提交，message 说人话
git add -A && git commit -m "进度条：滚动监听加节流与卸载清理"

# 3. 阶段性回看——这条命令能救你的命
git diff HEAD~1 --stat        # 上一次提交动了哪些文件
```

另外一个防呆技巧：让 agent 自己维护一条「任务分支上的提交清单」，你在验收时对着清单核对 diff 范围，比逐文件翻快得多。

## 第 3 步：实战——完整跑一个功能

拿一个真实需求从头走到尾：给博客的文章页加一条顶部阅读进度条。全程人工打字不到十行提示词，其余是验收。

### 3.1 让 agent 先读，再出方案（不要写代码）

```text
先阅读 components/toc.tsx 和 app/posts/[slug]/page.tsx，理解文章页的结构。
然后给「文章顶部加一条阅读进度条」出两套方案：
A. 纯 CSS 方案（scroll-timeline 或类似机制）
B. 组件化方案（React 组件 + scroll 监听）
对比两套方案的浏览器兼容性、维护成本，给出你的推荐。不要写代码。
```

两个关键词：**「先读再写」**和**「不要写代码」**。不提前拦住，agent 会立刻生成三百行——那三百行会占满它的上下文，反过来污染后面的讨论。方案阶段它的回答应该是人类语言，你至少能判断对错。

agent 返回后我做了一个真实决策：A 方案的 scroll-timeline 在目标浏览器支持度不够，选 B，但要限制组件边界。

### 3.2 选方案，补上它猜不到的约束

```text
用 B 方案，做成独立组件 ReadingProgress，放在 components/ 下。
约束：
1. 颜色用现有 CSS 变量 var(--accent)，不新造颜色；
2. 滚动监听必须节流，组件卸载时移除监听；
3. 不改 toc.tsx；
4. 完成的定义：npx tsc --noEmit 通过，npm run build 通过。
```

第 4 条就是从规则文件里继承的验收标准——正式交付的 prompt 里再写一遍，是给这一步上双保险。

### 3.3 它写码，你盯范围

这一步你的工作从「写」变成「盯」：它开始读文件、建组件、跑 typecheck。中途它可能停下来问「进度条要不要显示百分比数字」——这就是规则文件里「不确定的事直接问」生效的样子，答一句即可。

### 3.4 人审 diff：三个问题

代码写完不是终点。看 diff 时我只关心三件事：

- **范围对不对**：`git status` 里除了新组件和文章页，有没有多出来的文件？（它顺手格式化过什么？）
- **边界处理了吗**：组件卸载时监听器移除了吗？文章很短、进度不满一格时样式对吗？
- **有没有夹带私货**：为改一行而重构整个函数、给别人的代码加注释，这些都是要打回去的噪音。

### 3.5 验证、提交、让它写总结

```text
逐条验收：
1. 跑 npx tsc --noEmit 并给出退出码；
2. 跑 npm run build 确认通过；
3. 给我列出改动文件清单和每个文件改动原因。
不要自行提交。
```

全绿之后我来提交（`git add -A && git commit`），最后一步让它基于 diff 写一段实现说明——放进提交信息或笔记。它比谁都清楚自己改了什么，这段说明以后翻历史时价值极高。

这五步跑顺之后，一次循环大概十分钟，产出的是一个你**能解释**的功能。这才叫 vibe：节奏是快的，账是清楚的。

## 四、四个提示词模板：调试、重构、写新模块、改 bug 之外的事

工作流是骨架，日常高频的是下面四个模板。每个给真实写法，不是原则性空话。

### 4.1 调试模板：把「案发现场」完整押送过去

调试的质量取决于你喂的证据链。错误现场四件套：**完整报错原文、复现步骤、相关文件、你已经试过什么**。

```text
Bug：滚动到文章中部时进度条跳回 0。

报错/现象：无报错；进度条宽度在特定滚动位置闪回 0，约每 5 秒一次。
复现：打开任意文章，慢速滚动到 40% 附近。
相关代码：components/ReadingProgress.tsx（全文见附件）。
已试过：换 passive 监听无效；怀疑是文章页某个组件重渲染导致。

先给三个最可能的假设，按可能性排序，再说你怎么逐一验证。不要写码。
```

注意最后一句还是「不要写码」——先假设后验证，是调试模板的灵魂。agent 按假设排序后，会主动去读它怀疑的文件找证据，往往第二轮对话就锁定真凶（我的案例里是父组件的定时刷新导致进度条组件重挂载）。

### 4.2 重构模板：先画「现状图」和「目标图」

跨文件重构最容易翻车的是一致性。模板分两段：

```text
阶段一：现状盘点
阅读 components/learn/ 下所有以 card 命名的组件，列出：
每个组件的 props、被谁引用、样式来源。
输出一张清单，不要改任何文件。

阶段二：执行（我确认清单后才发）
把 props 传值统一改为 context：
- 新建 LearnCardContext，保留类型定义在单独文件
- 每改完一个组件跑一次 tsc，全绿再改下一个
- 最后给我「改了什么 + 哪些地方行为可能变化」清单
```

阶段一产出的清单你自己先看——agent 的全局理解对不对，在动手前就能判断，这时纠正的成本是零。

### 4.3 写新模块模板：给「完成」下一个可执行的 defini

```text
新模块：scripts/generate-reading-stats.mjs
需求：扫描 content/posts 下所有 mdx，输出每篇字数与预计阅读时长到
public/reading-stats.json。

完成的定义：
1. node scripts/generate-reading-stats.mjs 能跑通并生成合法 JSON；
2. 空 frontmatter、空文件的边界情况不报错；
3. 不引入新依赖；
4. 代码通过 tsc 检查（脚本也在 tsconfig 范围内）。
```

把边界情况直接写进完成定义，agent 的交付质量会上一个台阶——它默认只修主路径，你不点名边界它就当不存在。

### 4.4 「让 agent 自查」模板

```text
review 你刚才的全部改动，按下面的清单逐条回答：
1. 有没有未处理的错误路径（fetch 失败、数组越界、JSON 解析）？
2. 有没有未清理的资源（监听器、定时器、打开的连接）？
3. 有没有违反本仓库规则文件的条目？
4. 有没有「为了实现而实现」的多余改动？
只报告问题和建议，不要直接改。
```

自查能拦下三成左右的问题，而且比你逐行看快。最后一条尤其好用——它对「自己手痒」这件事有自知之明。

## 五、上下文管理：会话生命周期

agent 的能力上限，八成取决于上下文里装了什么。我的会话管理规则：

- **一个任务一个会话**。换任务就开新的。会话聊得越久，早期的重要结论被稀释得越厉害，它会开始重复你早就否掉过的方案——那不是它变笨，是上下文腐烂。
- **喂证据，别喂转述**。报错就给完整报错原文加对应文件，别描述「大概是哪个函数出问题了」。你的每次转述都在丢信息，它的每次猜测都在放大误差。
- **长任务写存档**。连续工作超过半小时，让它把「当前进度、已做决策、下一步计划」写进一个 markdown 存档：

```text
把这次任务的进展写进 docs/progress-reading-progress.md：
已完成什么、关键决策及理由、下一步做什么、有哪些未解决问题。
```

之后无论开新会话还是第二天回来，第一句就是「读 docs/progress-reading-progress.md，继续」——比从聊天记录考古可靠得多。

- **跨会话的事实进规则文件，会话内的事实进存档文件**。两个文件分工明确，agent 的「记忆」问题就解决了八成。

## 六、八条踩坑实录

每一条都付过学费：

1. **一行 prompt 甩大需求**。「帮我加个搜索功能」这种 prompt 的产出，一定是一个你没法验收的黑箱。拆到「方案—确认—实现—验收」四步，每步一次对话。
2. **无验收接受**。它说「完成了」你就信了。之后 typecheck 过不过、边界处理没处理，全是隐藏债务。验收标准写进 prompt，交付时要求它贴出验证结果。
3. **上下文塞爆**。把十几个文件全读进会话再提需求，关键指令被稀释，它开始答非所问。按需喂文件，其他用文件路径代替。
4. **让它自由发挥部署**。CI 配置、发布脚本、服务器操作——它改完构建照样绿，坏的是两周后的一次发布。部署相关一律「只出方案」。
5. **一次性接受百行 diff**。人审 diff 的耐心是有限的，百行以上的 diff 审察质量断崖下跌。用「小步提交」把每次审的量控制在一屏内。
6. **在同一个会话里连做三个任务**。第三个任务时它开始混淆前两个任务的约束。会话是易耗品，用完即弃。
7. **把它的话当文档**。它描述自己「已删除监听器」，diff 里根本没有。口头交付不算交付，一切以 diff 和命令输出为准。
8. **该自己写的时候也在 vibe**。安全、鉴权、数据库迁移、你看不懂的核心算法——这些写坏的成本远超省下的时间。vibe 的前提是你能验收，验收不了的部分先补课，或者老老实实手写。

## 七、结语：它是加速器，不是自动驾驶

用了大半年之后，我对 Vibe Coding 的定义收敛成一句话：**它把「写代码」从核心技能变成了元技能，把你的时间挤压到只剩三件事值得人做——定规格、做决策、负责任。**

它没有降低门槛，是抬高了天花板：以前你想清楚一个需求要写两天，现在想清楚就能当天上线；但「想清楚」本身，反而比以前更重要了。

下一篇是横向测评：Claude Code、Codex CLI、OpenCode、DeepSeek Harness、Windsurf、Trae、Qoder、CodeBuddy、ZCode，加上 WorkBuddy、百度搭子、豆包这些办公与通用平台，外加 DeepSeek / GLM 引擎与 OpenRouter——同一组任务跑了个遍，每款都写了上手体验、任务表现与适用场景，怎么选见分晓。
