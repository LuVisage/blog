## 「不碰键盘」是个误会

2025 年 2 月，Andrej Karpathy 给这种写法起了名字：全靠提示词，看着 AI 生成，几乎不亲自看 diff——他管这叫 vibe coding，还特意补了一句，这适合周末玩玩的小项目，不适合正经工程。

两年过去，这个词活了下来，但它的含义已经被用歪了。今天说 Vibe Coding，真正可持续的版本其实是：

> **AI 负责打字，你负责规格、验收和架构。**

差别就在最后半句。Karpathy 描述的那种「不看代码」我试过，结局都一样：生成的时候很爽，两周之后代码库变成一滩你说不清为什么能跑的泥。而我后来稳定产出的方式，恰恰是每一步都看——只是看的从「每一行怎么写」换成了「每一层对不对」。

这篇是实操教程：从开工前的准备，到一套可复用的工作流，再到四种提示词模式和踩坑清单。工具怎么选看下一篇横评，这篇假设你已经有一个能跑的 coding agent。

## 一、开工前的三件事

### 1. 规则文件：把「你希望它是什么样的人」写下来

每个像样的 coding agent 都支持项目级规则文件——Claude Code 读 `CLAUDE.md`，各家 IDE 有各自的规则目录，而越来越多的工具直接认社区的通用约定 `AGENTS.md`。这是性价比最高的一步：写一次，所有会话生效。

我的模板就五段，加起来不到五十行：

```markdown
# 项目约定

## 技术栈
- Next.js 15（App Router，静态导出）+ React 19 + TypeScript strict
- 样式走 CSS 变量与 Tailwind，不引入新 UI 库

## 必须遵守
- 改完必须跑 `npm run typecheck`，通过才算完成
- 不新增依赖；确需新增，先说明理由并停下等确认
- 内容文件（content/）里不允许出现 emoji

## 代码风格
- 注释只写「为什么」，不复述「做了什么」
- 优先修改现有文件，不轻易新建平行实现

## 禁区
- .github/workflows 与部署配置：改动前必须先说明意图
- 数据库迁移与鉴权逻辑：只出方案，不直接改
```

要点不是写得多全，而是写「**你怎么验收**」和「**哪里不许碰**」。agent 最大的问题是热情过度——你不划禁区，它连你的 CI 配置都敢顺手优化。

### 2. Git 纪律：Vibe Coding 的安全网

agent 会错，而且错得理直气壮。唯一能让你放开手脚的保障是：**任何时刻都能一键回到上一个好状态**。

三个习惯就够：

- **一个任务一个分支**，别在 main 上让 agent 直接跑；
- **每完成一个可验证的小步就提交**，commit message 说人话（「修复歌词区高度」而不是「update」）；
- 改动前后各跑一次构建，构建产物干净才进下一步。

有了这张网，你才敢对 agent 说「这个方案不行，回退，换条路」——而这恰恰是 vibe 的前提。

### 3. 想清楚「验收」是什么

这是新手和老手最大的分野。新手写提示词：「帮我加一个搜索功能」。老手写：「加搜索功能，**验收标准：typecheck 通过、首页搜索框可输入、空结果有占位提示、不新增依赖**」。

验收标准写进 prompt，等于把「完成」的定义权握在自己手里。否则 agent 会用「看起来像完成了」来交差。

## 二、一套可以直接抄的工作流

以一个真实需求为例——假设要给博客加个「阅读进度百分比」的小功能。整个流程五步，全程人工打字不超过十行。

### 第 1 步：让 agent 先读，再出方案

```
先阅读 components/toc.tsx 与 app/posts/[slug]/page.tsx，理解现有结构。
然后给出给文章页加顶部阅读进度条的两套方案（纯 CSS / 组件化），
对比优劣。不要写代码。
```

两个关键词：**「先读再写」**和**「不要写代码」**。不提前拦住，agent 会立刻生成三百行——而那三百行会占据它的上下文，反过来污染后面的讨论。先让方案过你的眼，成本最低。

### 第 2 步：选方案，补约束

你从两套方案里挑一个（或者各砍一半拼一个），然后补上它猜不到的约束：

```
用组件化方案。进度条颜色用现有的 --accent 变量，滚动监听要节流，
卸载时清理监听器。不要动 toc.tsx。
```

### 第 3 步：实现 + 自带验收

```
按上面的讨论实现。完成的定义：npx tsc --noEmit 通过，
滚动时进度条平滑更新，文章底部不存在残留监听器。
完成后把改动文件列表和验证结果给我，不要自行提交。
```

「不要自行提交」很重要——提交前你要亲眼看 diff，这一步永远是人的。

### 第 4 步：人审 diff

这不是走形式。你要看的不是每一行，而是三个问题：

- **改动范围对吗**——它有没有偷偷碰不该碰的文件？
- **边界处理了吗**——卸载清理、空值、极端长度？
- **有没有「为了实现而实现」**—— agent 特别喜欢顺手重构、加注释、改格式，这些噪音会污染你的提交。

### 第 5 步：验证、提交、让 agent 写总结

验收标准逐条跑一遍。过了就提交，然后让 agent 基于这次 diff 写一段实现说明，放进 PR 描述或笔记——它比谁都清楚自己改了什么。

这五步跑顺之后，一次循环大概十分钟，产出的是一个你**能解释**的功能。这才叫 vibe：节奏是快的，账是清楚的。

## 三、四种提示词模式

工作流是骨架，日常用得最多的是这四种模式：

**计划先行**。凡是预计超过两个文件的改动，先要计划再要代码。一句万能开头：「先读相关代码，再给方案，不要写代码。」它强制 agent 建立上下文，也强制你想清楚。

**约束前置**。把技术栈、禁改文件、风格要求放在会话开头说，而不是等它犯了再纠正。纠正一次要花三轮对话，前置只要一句。

**验收内嵌**。每个任务都带完成定义：「完成的标准是测试通过且构建干净」。agent 对「可验证的完成」的执行力惊人——前提是你给了可验证的标准。

**让 agent 自查**。写完让它自己review：「检查你刚才的改动：有没有未处理的错误路径、未清理的资源、以及与项目现有约定的冲突。」自查能拦下大概三成的低级问题，而且比你自己逐行看快得多。

## 四、上下文是货币

agent 的能力上限，八成取决于上下文里装了什么。几个实操结论：

- **会话是易耗品**。换任务就开新会话，别在同一个对话里从需求聊到部署——聊到后面它开始重复早前的错误结论，那不是它变笨了，是上下文腐烂了。
- **喂文件，别喂猜测**。报错就直接给它完整报错和对应文件，别描述「大概是哪个函数出问题了」——你的转述会丢失它需要的细节。
- **长任务中途让它存档**。连续工作半小时后让 agent 把当前进度、关键决策写进一个 markdown，之后新会话从这个文件复活，比从聊天记录里考古可靠得多。
- **它的记忆没有你想的可靠**。跨会话的事实（约定、决策）写进规则文件和存档文件，别指望它「上次说过了」。

## 五、哪些环节一步都不能让

Vibe Coding 有边界，越过就是事故：

- **安全与鉴权**：session 处理、密钥管理、SQL 拼接——agent 会给你「能跑」的版本，而安全代码的价值恰恰在它不能跑的那些路径上。这类代码让 agent 出方案，人写、人审。
- **数据迁移**：一条 ALTER TABLE 搞坏生产库的事故，agent 不会替你承担。
- **你完全不懂的领域**： vibe 的前提是你能验收。看不懂 diff 的地方，先补课再动手——这也是我坚持「让 agent 出方案而不是直接写码」的深层原因：方案是人类语言，你至少能判断对错。
- **第三方的钱和你的钥匙**：涉及支付、计费、密钥轮换的代码，逐行人审，没有例外。

## 六、结语：它是加速器，不是自动驾驶

用了大半年之后，我对 Vibe Coding 的定义收敛成一句话：**它把「写代码」从核心技能变成了元技能，把你的时间挤压到只有三件事值得人做——定规格、做决策、负责任。**

它没有降低门槛，是抬高了天花板：以前你想清楚一个需求要写两天，现在想清楚就能当天上线；但「想清楚」本身，反而比以前更重要了。

下一篇是横向测评：Claude Code、Codex CLI、OpenCode、DeepSeek Harness、Windsurf、Trae、Qoder、CodeBuddy、ZCode 这些 agent，加上 WorkBuddy、百度搭子、豆包这些办公与通用平台，外加 DeepSeek / GLM 引擎与 OpenRouter——同一组任务跑了个遍，怎么选见分晓。
