## Day1 核心：Dockerfile 怎么写

### 一个"能跑但很差"的 Dockerfile

```dockerfile
FROM python:3.11
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
CMD ["uvicorn", "app:app", "--host", "0.0.0.0"]
```

**问题**：

| 问题 | 后果 |
| --- | --- |
| 基础镜像 1GB+ | 体积巨大，推送慢 |
| `COPY . /app` 在前 | **改一行代码就重装所有依赖**（构建 5 分钟） |
| 没有 `.dockerignore` | `.venv` / `.git` / 数据文件全被打进去 |
| 用 root 运行 | 安全风险 |
| 没有 `requirements.txt` 的版本锁定 | 每次构建结果不同 |
| `CMD` 用 shell 形式的字符串 | 信号无法正确传递给进程 |

### 生产级的 Dockerfile（多阶段构建）

```dockerfile
# ============ 阶段 1: 构建依赖 ============
FROM python:3.11-slim AS builder

WORKDIR /build

# ★ 先只复制依赖声明 —— 依赖没变时这一层会被缓存
COPY pyproject.toml README.md ./
COPY src/ ./src/

# 装到独立目录，便于复制到运行阶段
RUN pip install --no-cache-dir --prefix=/install .

# ============ 阶段 2: 运行时 ============
FROM python:3.11-slim

# 创建非 root 用户
RUN groupadd -r app && useradd -r -g app app

# 时区与基础工具（按需）
ENV TZ=Asia/Shanghai \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

# ★ 只复制装好的依赖，不带编译工具链
COPY --from=builder /install /usr/local

# ★ 先复制依赖声明
COPY pyproject.toml README.md ./
# ★ 再复制代码（代码改动不会影响依赖层缓存）
COPY src/ ./src/

RUN pip install --no-cache-dir --no-deps -e .

# 切换到非 root
USER app

EXPOSE 8000

# ★ 健康检查（让 Docker 知道容器是否正常）
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request,sys; \
        sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health').status==200 else 1)"

# ★ 用 JSON 数组形式（exec form）—— 信号能正确传递
CMD ["uvicorn", "demo_service.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**五个关键优化**：

| 优化 | 效果 |
| --- | --- |
| **多阶段构建** | 最终镜像不含编译工具，体积从 1.2GB 降到 200MB |
| **先 COPY 依赖声明** | 改代码不会重装依赖，构建从 5 分钟到 10 秒 |
| **非 root 用户** | 容器逃逸时攻击面更小 |
| **`HEALTHCHECK`** | Docker 能知道容器状态，配合 compose 的依赖顺序 |
| **exec form 的 CMD** | `docker stop` 时信号能传到 uvicorn，优雅关闭 |

### `.dockerignore`（必须）

```
.venv/
venv/
__pycache__/
*.pyc
.git/
.gitignore
.pytest_cache/
.mypy_cache/
.ruff_cache/
.env
*.log
data/
logs/
tests/
docs/
*.md
!README.md
```

**没有它会发生什么**：

```
你的 .venv 有 500MB，.git 有 100MB，data/ 有 2GB
-> 全被打进构建上下文
-> 每次构建都要传输 2.6GB
-> 构建从 10 秒变成 5 分钟
```

> **`docker build` 的第一件事是把整个目录发给 Docker daemon** —— 所以 `.dockerignore` 直接影响构建速度。

### 层缓存的原理（这是 Day1 最重要的认知）

Docker 镜像是一层层的，**每一层都会缓存，只要该层的输入没变就复用**：

```dockerfile
COPY pyproject.toml ./          # ← 层 A：依赖声明没变 -> 命中缓存
RUN pip install .               # ← 层 B：A 没变 -> 命中缓存，跳过安装！
COPY src/ ./src/                # ← 层 C：代码变了 -> 缓存失效，重新执行
```

**所以顺序是**：`不变的在前，常变的在后`。

```dockerfile
# ✗ 顺序错了
COPY . .                        # ← 改一行代码，这层就变了
RUN pip install -r req.txt      # ← 于是这层也要重跑（5 分钟）

# ✓ 正确顺序
COPY requirements.txt .         # ← 依赖很少变
RUN pip install -r requirements.txt
COPY . .                        # ← 代码常变，放最后
```

## Day2 核心：docker-compose 一键启动

**这是本周最实用的产出。**

```yaml
# docker-compose.yml
name: demo-api

services:
  # ============ API 服务 ============
  api:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: demo-api
    restart: unless-stopped
    env_file: .env
    environment:
      # ★ 用服务名做主机名（compose 内置 DNS）
      DATABASE_URL: postgresql+asyncpg://postgres:${POSTGRES_PASSWORD}@postgres:5432/demo
      REDIS_URL: redis://redis:6379/0
    ports:
      - "8000:8000"
    depends_on:
      postgres:
        condition: service_healthy        # ★ 等数据库真的就绪，而不只是启动
      redis:
        condition: service_started
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/health').status==200 else 1)"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 15s
    networks: [backend]

  # ============ PostgreSQL ============
  postgres:
    image: postgres:16-alpine
    container_name: demo-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: demo
    volumes:
      - pgdata:/var/lib/postgresql/data          # ★ 数据持久化
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d demo"]
      interval: 5s
      timeout: 3s
      retries: 10
    # ★ 不暴露端口到宿主机（只让 compose 内部访问，更安全）
    # ports:
    #   - "5432:5432"       # 只在需要本地连数据库调试时才开
    networks: [backend]

  # ============ Redis ============
  redis:
    image: redis:7-alpine
    container_name: demo-redis
    restart: unless-stopped
    command: >
      redis-server
      --appendonly yes
      --maxmemory 256mb
      --maxmemory-policy allkeys-lru
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [backend]

  # ============ Nginx（Week4 Day3）============
  nginx:
    image: nginx:alpine
    container_name: demo-nginx
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/certs:/etc/nginx/certs:ro
      - ./nginx/www:/var/www/certbot:ro
    depends_on:
      api:
        condition: service_healthy
    networks: [backend]

volumes:
  pgdata:
  redisdata:

networks:
  backend:
    driver: bridge
```

### 关键设计解读

| 设计 | 为什么 |
| --- | --- |
| **`depends_on` + `condition: service_healthy`** | 只写 `depends_on` 只等"启动"，不等"就绪"，API 会在数据库还没准备好时启动失败 |
| **`restart: unless-stopped`** | 服务器重启后自动拉起（`always` 会在你手动停止后也重启） |
| **`volumes` 持久化** | 否则 `docker compose down` 数据全丢 |
| **不暴露 Postgres 端口** | 只让内部网络访问，减少攻击面 |
| **服务名做主机名** | compose 内置 DNS，用 `postgres` 而不是 IP |
| **`.env` 提供密码** | 密码不能硬编码在 compose 文件里（会提交到 git） |

### 常用命令

```bash
docker compose up -d                  # 后台启动全部
docker compose up -d --build          # 重新构建并启动
docker compose logs -f api            # 跟踪 api 日志
docker compose ps                     # 查看状态与健康
docker compose exec api bash          # 进容器
docker compose exec postgres psql -U postgres -d demo    # 连数据库
docker compose down                   # 停止（保留数据卷）
docker compose down -v                # 停止并删除数据卷（★ 数据会丢）
docker compose restart api            # 只重启 api
```

### 数据库迁移在什么时机执行

**问题**：代码更新了模型，什么时候跑 `alembic upgrade head`？

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| **手动** | 部署后手动执行 | 简单但容易忘 |
| **容器启动时** | 在 entrypoint 里跑迁移 | 多实例同时启动会冲突 |
| **独立 job** | compose 里加一个一次性的 migrate 服务 | 推荐 |

```yaml
  migrate:
    build: .
    command: alembic upgrade head
    env_file: .env
    depends_on:
      postgres:
        condition: service_healthy
    restart: "no"                        # 一次性任务
```

```bash
docker compose run --rm migrate        # 部署前执行
docker compose up -d api               # 再起服务
```

## Day3 核心：Nginx 与 SSE 的缓冲坑

**这是 Week2 Day4 埋下的坑，在这里必须解决。**

```nginx
# nginx/nginx.conf
events { worker_connections 1024; }

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    log_format json_combined escape=json
        '{"ts":"$time_iso8601","remote":"$remote_addr","method":"$request_method",'
        '"uri":"$request_uri","status":$status,"bytes":$body_bytes_sent,'
        '"rt":$request_time,"ua":"$http_user_agent"}';
    access_log /var/log/nginx/access.log json_combined;

    # ---- 限流（与应用的 Redis 限流互补）----
    limit_req_zone $binary_remote_addr zone=api:10m rate=30r/s;

    upstream api_backend {
        server api:8000;
        keepalive 32;
    }

    # HTTP -> HTTPS 跳转
    server {
        listen 80;
        server_name your-domain.com;

        # Let's Encrypt 验证
        location /.well-known/acme-challenge/ {
            root /var/www/certbot;
        }
        location / {
            return 301 https://$host$request_uri;
        }
    }

    server {
        listen 443 ssl;
        http2 on;
        server_name your-domain.com;

        ssl_certificate     /etc/nginx/certs/fullchain.pem;
        ssl_certificate_key /etc/nginx/certs/privkey.pem;
        ssl_protocols TLSv1.2 TLSv1.3;

        # ---- ★★★ 流式输出的关键配置 ★★★ ----
        location /api/v1/chat/stream {
            proxy_pass http://api_backend;
            proxy_http_version 1.1;

            proxy_buffering off;              # ★ 关掉响应缓冲
            proxy_cache off;                  # ★ 关掉缓存
            chunked_transfer_encoding on;
            proxy_set_header Connection '';   # 保持长连接

            proxy_read_timeout 300s;          # ★ 长连接要放宽超时
            proxy_send_timeout 300s;

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
        # ---- 流式配置结束 ----

        location /api/ {
            limit_req zone=api burst=50 nodelay;
            proxy_pass http://api_backend;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            proxy_set_header Connection '';
        }

        location / {
            root /var/www/html;
            try_files $uri $uri/ /index.html;
        }
    }
}
```

**必须记住的三行**：

```nginx
proxy_buffering off;              # 没有它，SSE 会被攒成一次性返回
proxy_cache off;                  # 没有它，可能返回缓存的旧响应
proxy_read_timeout 300s;          # 没有它，长回答会在 60 秒被切断
```

**这是 Week2 Day4 那个坑的最终答案**：
- 应用层：`X-Accel-Buffering: no`（告诉 Nginx 别缓冲这个响应）
- Nginx 层：`proxy_buffering off`（全局关掉）
- **两层都要做**，因为 `X-Accel-Buffering` 需要 Nginx 显式支持，而 `proxy_buffering off` 是兜底。

### HTTPS 证书

```bash
# 用 certbot 申请（不需要停 Nginx）
docker run --rm \
  -v "$(pwd)/nginx/certs:/etc/letsencrypt" \
  -v "$(pwd)/nginx/www:/var/www/certbot" \
  certbot/certbot certonly --webroot \
  -w /var/www/certbot \
  -d your-domain.com \
  --email you@example.com --agree-tos --no-eff-email

# 自动续期（加到 crontab）
0 3 * * * docker run --rm -v /path/nginx/certs:/etc/letsencrypt \
  certbot/certbot renew --quiet && docker compose exec nginx nginx -s reload
```

**为什么必须 HTTPS**：

| 理由 | 说明 |
| --- | --- |
| **浏览器标记"不安全"** | 用户的信任直接崩掉 |
| **JWT token 明文传输** | HTTP 下中间人可以直接拿到 token |
| **CORS 与部分 API 限制** | 某些浏览器 API 要求 HTTPS |
| **免费** | Let's Encrypt 完全免费 |

### 首次登录与基础加固

```bash
# ① 从本地登录（用密钥对，不用密码）
ssh root@your-server-ip

# ② 创建普通用户（不要一直用 root）
adduser deploy
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh
cp ~/.ssh/authorized_keys /home/deploy/.ssh/
chown -R deploy:deploy /home/deploy/.ssh
chmod 700 /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys

# ③ 禁止 root 密码登录
sed -i 's/^#*PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart sshd

# ④ 防火墙：只开必要端口
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp        # SSH
ufw allow 80/tcp        # HTTP（Let's Encrypt 验证需要）
ufw allow 443/tcp       # HTTPS
ufw enable

# ⑤ 安装 Docker
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy        # 让 deploy 用户能用 docker
```

** 安全红线**：

| 红线 | 原因 |
| --- | --- |
| **不用 root 跑服务** | 一旦被攻破，攻击者拿到最高权限 |
| **不用密码登录 SSH** | 会被暴力爆破（日志里每天几万次尝试） |
| **不开 5432 / 6379 到公网** | 数据库直接被扫库（真的会发生） |
| **`.env` 权限设 600** | 别的用户读不到 |
| **定期更新系统** | `apt update && apt upgrade` |

### 一键部署脚本

```bash
#!/usr/bin/env bash
# deploy.sh
set -euo pipefail              # ★ 任何命令失败就退出，未定义变量报错

APP_DIR="/home/deploy/demo-api"
cd "$APP_DIR"

echo "==> 拉取最新代码"
git pull --ff-only

echo "==> 检查 .env"
if [ ! -f .env ]; then
    echo "错误: 缺少 .env 文件（可从 .env.example 复制）" >&2
    exit 1
fi
chmod 600 .env                 # ★ 收紧权限

echo "==> 构建镜像"
docker compose build --pull

echo "==> 执行数据库迁移"
docker compose run --rm migrate

echo "==> 重启服务"
docker compose up -d --remove-orphans

echo "==> 等待健康检查"
for i in $(seq 1 30); do
    if curl -fsS http://localhost/health > /dev/null 2>&1; then
        echo "✓ 部署成功"
        exit 0
    fi
    sleep 2
done

echo "✗ 健康检查失败，查看日志:" >&2
docker compose logs --tail=50 api >&2
exit 1
```

**脚本里的三个工程要点**：

| 要点 | 说明 |
| --- | --- |
| `set -euo pipefail` | 失败立即退出，不会带着一半状态继续 |
| **迁移在重启之前** | 否则新代码可能访问不存在的字段 |
| **健康检查等待** | 部署脚本要能判断成功与否（CI 要用） |

## Day5 核心：CI/CD 与监控

### GitHub Actions

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

jobs:
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: testpass
          POSTGRES_DB: testdb
        ports: ["5432:5432"]
        options: >-
          --health-cmd pg_isready --health-interval 5s
          --health-timeout 3s --health-retries 10

      redis:
        image: redis:7
        ports: ["6379:6379"]
        options: >-
          --health-cmd "redis-cli ping" --health-interval 5s
          --health-timeout 3s --health-retries 5

    env:
      DATABASE_URL: postgresql+asyncpg://postgres:testpass@localhost:5432/testdb
      REDIS_URL: redis://localhost:6379/0
      JWT_SECRET: ci-test-secret-at-least-16-chars

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip

      - name: 安装依赖
        run: pip install -e ".[dev]"

      - name: 代码风格检查
        run: ruff check .

      - name: 类型检查
        run: mypy src/

      - name: 运行测试
        run: pytest --cov=src --cov-report=term-missing --cov-fail-under=60

      - name: 构建镜像（验证 Dockerfile 可用）
        run: docker build -t demo-api:test .

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: 部署到服务器
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_KEY }}
          script: |
            cd /home/deploy/demo-api
            ./deploy.sh
```

**CI 的价值不只是"自动跑测试"**：

| 检查项 | 拦住的问题 |
| --- | --- |
| `ruff check` | 未使用的 import、潜在 bug |
| `mypy` | 类型错误 |
| `pytest --cov-fail-under=60` | 覆盖率下降 |
| `docker build` | **Dockerfile 改坏了但在本地没测** |

> **最后一条很关键**：很多人 CI 里只跑测试，不构建镜像。结果部署时才发现 Dockerfile 有问题。

### 监控与告警

**三个层次的监控**：

| 层次 | 指标 | 工具 |
| --- | --- | --- |
| **基础设施** | CPU / 内存 / 磁盘 / 网络 | `docker stats` / Netdata |
| **应用** | QPS / 延迟 P95 / 错误率 / 并发数 | 应用埋点 + Prometheus |
| **业务** | LLM 调用量 / 花费 / 每个用户的 token 数 | 自定义指标 |

**最低成本的方案**（学习期推荐）：

```bash
# ① 容器资源
docker stats --no-stream

# ② 磁盘（最容易出问题 —— 满了服务就挂）
df -h

# ③ 日志里搜错误
docker compose logs --since 1h api | grep -c '"level": "ERROR"'
```

**一个必须配的告警**：**磁盘使用率 > 85%**。

```
Docker 的日志和数据卷会持续增长：
  · 容器日志默认无限增长（要在 compose 里配 max-size）
  · Postgres 的 WAL 会占用空间
  · 磁盘满了 -> Postgres 拒绝写入 -> 服务挂掉
```

**限制容器日志大小**（必须在 compose 里加）：

```yaml
services:
  api:
    logging:
      driver: "json-file"
      options:
        max-size: "10m"          # 单个日志文件最大 10MB
        max-file: "3"            # 最多保留 3 个
```

> **这是一条很容易被忽略但极其重要的配置**：不配的话，运行几周后磁盘会被日志写满。

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 改代码后镜像没更新 | 层缓存 | `docker compose build --no-cache` |
| 构建极慢 | 没写 `.dockerignore` | 加上 |
| 改一行代码就重装依赖 | COPY 顺序错 | 依赖声明放前面 |
| 本地能跑容器里不行 | 环境变量没传 | 检查 `env_file` / `environment` |
| API 启动时数据库还没好 | `depends_on` 只等启动 | `condition: service_healthy` |
| 数据重启就丢 | 没配 `volumes` | 加数据卷 |
| **SSE 变成一次性返回** | **Nginx 缓冲** | `proxy_buffering off` |
| 长回答被切断 | 默认 60s 超时 | `proxy_read_timeout 300s` |
| 容器里时间不对 | 时区没设 | `ENV TZ=Asia/Shanghai` |
| `docker stop` 后进程没优雅退出 | CMD 用了 shell 形式 | 用 exec form（JSON 数组） |
| 磁盘被日志写满 | 没限制日志大小 | `logging.options.max-size` |
| 数据库端口暴露到公网 | compose 里写了 `ports` | 去掉，只留内部网络 |
