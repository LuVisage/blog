## 4.2 为什么测试是工程能力的分水岭

**面试时最常被问的一句话**：

> "你怎么保证你的代码是对的？"

| 回答 | 面试官的判断 |
| --- | --- |
| "我跑了一下，看起来没问题" | 脚本思维 |
| "我写了几条单测，覆盖了边界情况和异常路径" | **工程思维** |

**测试的三个实际价值**（不只是"正确性"）：

| 价值 | 说明 |
| --- | --- |
| **重构的底气** | 改完代码跑一遍测试，就知道有没有改坏 |
| **文档** | 测试用例是最准确的「这个函数怎么用」的说明 |
| **设计压力** | 难测的代码 = 耦合太紧的代码，测试会逼你解耦 |

> **一个经验**：如果一段代码很难写测试（比如需要真实数据库、真实 API），那它大概率**耦合过紧** —— 测试的难度是设计的信号。

## 4.3 pytest 基础

### 4.3.1 第一个测试

```python
# test_calc.py
def add(a: int, b: int) -> int:
    return a + b

def test_add_positive():
    assert add(1, 2) == 3

def test_add_negative():
    assert add(-1, -2) == -3

def test_add_zero():
    assert add(0, 5) == 5
```

运行：

```bash
pytest test_calc.py -v
```

**三条约定**：

| 约定 | 说明 |
| --- | --- |
| 文件名 `test_*.py` 或 `*_test.py` | pytest 自动发现 |
| 函数名 `test_*` | 自动收集为测试 |
| 用 `assert` 断言 | 失败时 pytest 会打印详细的中间值 |

**pytest 的 assert 比 unittest 好在哪里**：

```python
def test_dict():
    a = {"x": 1, "y": [1, 2, 3]}
    b = {"x": 1, "y": [1, 2, 4]}
    assert a == b
```

pytest 会输出**完整的两边值差异**，而 `unittest.assertEqual` 只给一行说明。

### 4.3.2 测试异常

```python
import pytest

def parse_age(s: str) -> int:
    n = int(s)
    if n < 0:
        raise ValueError("年龄不能为负")
    return n

def test_parse_age_invalid():
    with pytest.raises(ValueError, match="不能为负"):
        parse_age("-1")

def test_parse_age_not_a_number():
    with pytest.raises(ValueError):
        parse_age("abc")
```

**`match=` 用正则匹配错误信息** —— 这很重要，否则任何 `ValueError` 都能通过测试。

### 4.3.3 参数化（一个测试覆盖多种输入）

```python
import pytest

@pytest.mark.parametrize("a,b,expected", [
    (1, 2, 3),
    (0, 0, 0),
    (-1, 1, 0),
    (100, -100, 0),
])
def test_add_parametrized(a, b, expected):
    assert add(a, b) == expected
```

**输出会显示 4 个独立的测试**：

```
test_calc.py::test_add_parametrized[1-2-3] PASSED
test_calc.py::test_add_parametrized[0-0-0] PASSED
...
```

**为什么参数化很重要**：边界情况不用写重复的函数，改起来方便，**而且一眼能看出覆盖了哪些情况**。

### 4.3.4 fixture：复用准备工作

```python
import pytest

@pytest.fixture
def sample_users():
    """提供一份测试用的用户数据"""
    return [
        {"id": 1, "name": "alice", "age": 30},
        {"id": 2, "name": "bob", "age": 25},
    ]

@pytest.fixture
def user_service(sample_users):
    """依赖上面的 fixture —— fixture 可以互相依赖"""
    return UserService(sample_users)

def test_get_user(user_service):
    u = user_service.get(1)
    assert u["name"] == "alice"

def test_list_users(user_service):
    assert len(user_service.list()) == 2
```

**fixture 的三个作用域**：

| scope | 生命周期 | 用途 |
| --- | --- | --- |
| `function`（默认） | 每个测试函数各一份 | 隔离性最好 |
| `module` | 每个测试文件一份 | 较重的准备 |
| `session` | 整个测试会话一份 | 最重的（如启动数据库） |

```python
@pytest.fixture(scope="session")
def db_engine():
    engine = create_engine("sqlite:///:memory:")
    yield engine
    engine.dispose()          # yield 之后的代码是清理逻辑
```

**`yield` 形式的 fixture = setup + teardown**。

→ **这替代了 `setUp` / `tearDown`，但更灵活**（可以按依赖组合）。

### 4.3.5 `conftest.py`

**放在 `tests/` 目录下的 `conftest.py` 里的 fixture 会自动对所有测试文件可用**，不需要 import。

```
tests/
├── conftest.py          # 公共 fixture 放这里
├── test_client.py
└── test_models.py
```

**这是组织测试的标准做法。**

## 4.4 mock：隔离外部依赖

**为什么需要 mock**：

| 依赖 | 为什么不能在测试里真的调用 |
| --- | --- |
| **LLM API** | 慢、要花钱、结果不确定 |
| **数据库** | 需要环境、状态互相污染 |
| **网络请求** | 不稳定、可能被限流 |
| **当前时间** | 无法复现 |
| **随机数** | 无法复现 |

### 4.4.1 `monkeypatch`（推荐，简单场景）

```python
def get_greeting() -> str:
    return f"hello at {datetime.now().isoformat()}"
    # 依赖"当前时间"，结果不可复现

def test_get_greeting(monkeypatch):
    class FakeDatetime:
        @classmethod
        def now(cls):
            return datetime(2026, 1, 1, 12, 0, 0)

    monkeypatch.setattr("mymodule.datetime", FakeDatetime)
    assert get_greeting() == "hello at 2026-01-01T12:00:00"
    # 测试结束后 monkeypatch 自动还原
```

### 4.4.2 `unittest.mock`（复杂场景）

```python
from unittest.mock import AsyncMock, MagicMock

async def test_summarize(monkeypatch):
    fake_response = MagicMock()
    fake_response.choices[0].message.content = "这是摘要"

    mock_client = MagicMock()
    mock_client.chat.completions.create = AsyncMock(return_value=fake_response)

    monkeypatch.setattr("mymodule.get_client", lambda: mock_client)

    result = await summarize("一段很长的文本")
    assert result == "这是摘要"
    mock_client.chat.completions.create.assert_awaited_once()   # 验证被调用了一次
```

** 注意异步要用 `AsyncMock`**，`MagicMock` 不能 await。

### 4.4.3 mock 的取舍

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| **mock 外部依赖** | 快、稳定、免费 | 测的是"你的逻辑"，不是"真的能跑通" |
| **真实调用** | 真实 | 慢、贵、不稳定 |

**推荐的分层策略**：

| 测试类型 | 数量 | 用什么 |
| --- | --- | --- |
| **单元测试** | 多（几十~几百） | mock 一切外部依赖 |
| **集成测试** | 少（几个） | 真实数据库（用 Docker 起），mock LLM |
| **端到端测试** | 极少（1~2 个） | 全真实（可以只在发布前跑） |

> **关键认知**：**mock 通过不代表功能正确**。mock 只能保证"你的逻辑在假定依赖正确时是对的"。所以必须有少量的真实集成测试。

## 4.5 异步测试

```python
import pytest

@pytest.mark.asyncio
async def test_async_fetch():
    result = await fetch_data()
    assert result is not None
```

**需要安装** `pytest-asyncio`，并在 `pyproject.toml` 里配置：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"        # 自动识别 async def 测试，不用写 @pytest.mark.asyncio
```

**测试并发行为**（用 mock 验证真的并发了）：

```python
@pytest.mark.asyncio
async def test_concurrent_execution():
    timeline = []

    async def fake_call(name, delay):
        timeline.append(f"{name}-start")
        await asyncio.sleep(delay)
        timeline.append(f"{name}-end")

    t0 = time.perf_counter()
    await asyncio.gather(fake_call("A", 0.1), fake_call("B", 0.1))
    elapsed = time.perf_counter() - t0

    # 并发执行的总耗时应该接近 max(0.1, 0.1) 而不是 0.2
    assert elapsed < 0.15
    # 两个任务应该"交错"执行
    assert timeline.index("B-start") < timeline.index("A-end")
```

**这个测试模式非常实用** —— 它能验证"我以为我写了并发，但其实是串行"这类 bug（Day3 的常见坑）。

## 4.6 日志：从 print 到结构化

### 4.6.1 为什么不能用 print

| print 的问题 | 后果 |
| --- | --- |
| 没有级别 | 无法区分"调试信息"和"严重错误" |
| 没有时间戳 | 无法排查时序问题 |
| 无法关闭 | 生产环境刷屏，拖慢性能 |
| 输出到 stdout | 无法按文件/服务收集 |
| **非结构化** | **无法按字段检索**（"查询用户 42 的所有错误"做不到） |

### 4.6.2 logging 基础

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)-8s %(name)s: %(message)s",
)
logger = logging.getLogger(__name__)        # ← 用 __name__ 作为 logger 名

logger.debug("调试细节")        # 生产环境不输出
logger.info("正常信息")
logger.warning("警告")
logger.error("错误")
logger.critical("严重")
logger.exception("带堆栈的错误")   # 只能在 except 块里用
```

**五个级别**（从低到高）：`DEBUG < INFO < WARNING < ERROR < CRITICAL`

**级别怎么选**：

| 级别 | 什么时候用 |
| --- | --- |
| DEBUG | 详细的内部状态（循环变量、中间结果） |
| INFO | 关键业务事件（请求开始、任务完成） |
| WARNING | 可以继续但需要注意（重试成功、降级） |
| ERROR | 操作失败但服务还能跑（一次 API 调用失败） |
| CRITICAL | 服务不可用（数据库连不上） |

### 4.6.3 结构化日志（生产环境的标准做法）

**问题**：这行日志怎么检索？

```
2026-01-01 12:00:00 ERROR 用户 42 查询订单失败
```

**正则匹配？脆弱且难维护。**

**结构化日志**：输出 JSON，每个字段独立。

```python
import json
import logging

class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        }
        # 把 extra={...} 传进来的字段也带上
        for k, v in record.__dict__.items():
            if k not in _RESERVED and not k.startswith("_"):
                payload[k] = v
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)

_RESERVED = set(logging.LogRecord("", 0, "", 0, "", (), None).__dict__)
```

**用法**：

```python
logger.info("查询用户", extra={"user_id": 42, "source": "api"})
```

**输出**：

```json
{"ts":"2026-01-01T12:00:00","level":"INFO","logger":"app","msg":"查询用户","user_id":42,"source":"api"}
```

**现在可以精确检索了**：

```
user_id:42 AND level:ERROR        <- 在生产日志系统（ELK / Loki）里直接查询
```

### 4.6.4 请求追踪（trace_id）

**问题**：一个请求经过 5 个服务，日志散落在各处，怎么串起来？

**解法**：给每个请求分配一个 `trace_id`，所有日志都带上它。

```python
import uuid
from contextvars import ContextVar

trace_id_var: ContextVar[str] = ContextVar("trace_id", default="-")

class TraceFilter(logging.Filter):
    """自动给所有日志加上当前请求的 trace_id"""

    def filter(self, record: logging.LogRecord) -> bool:
        record.trace_id = trace_id_var.get()
        return True

# 中间件里（Week2 会讲）
trace_id_var.set(uuid.uuid4().hex[:8])
```

**输出**：

```json
{"trace_id":"a1b2c3d4","msg":"收到请求","path":"/chat"}
{"trace_id":"a1b2c3d4","msg":"调用 LLM","model":"gpt-4"}
{"trace_id":"a1b2c3d4","msg":"完成","elapsed_ms":1234}
```

**用 `ContextVar` 而不是全局变量**：因为异步环境下多个请求会并发，全局变量会串号。`ContextVar` 是 asyncio 安全的。

> **这是 async 环境下做请求追踪的标准方案。**

### 4.6.5 日志的三条红线

| 红线 | 原因 |
| --- | --- |
| **绝不记录密码 / token / API Key** | 日志会被收集、导出、查看 |
| **不在循环里打 INFO 日志** | 一万条数据的循环打一万行日志会拖慢服务 |
| **不记录完整的用户隐私数据** | 合规问题（GDPR / 个人信息保护法） |

**敏感字段过滤**（Day2 讲过，这里再强调一次）：

```python
SENSITIVE = {"password", "token", "api_key", "secret", "authorization"}

def redact(data: dict) -> dict:
    return {k: ("***" if k.lower() in SENSITIVE else v) for k, v in data.items()}
```

## 4.7 配置管理（pydantic-settings）

**问题**：数据库密码、API Key 不能写在代码里。

```python
# ✗ 硬编码
DB_PASSWORD = "my_secret_password"       # 提交到 git 就泄漏了
API_KEY = "sk-xxxxx"
```

**正确做法：从环境变量读，并做类型校验。**

```python
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    """应用配置 —— 从环境变量或 .env 文件读取"""

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )

    # 应用
    app_name: str = "my-service"
    debug: bool = False

    # 数据库
    database_url: str = Field(description="Postgres 连接串")
    db_pool_size: int = Field(default=10, ge=1, le=100)

    # Redis
    redis_url: str = "redis://localhost:6379/0"

    # LLM
    openai_api_key: str = Field(description="OpenAI API Key")
    llm_model: str = "gpt-4o-mini"
    llm_timeout: float = Field(default=30.0, ge=1, le=300)

    # 安全
    jwt_secret: str = Field(description="JWT 签名密钥")
    jwt_expire_minutes: int = 60

settings = Settings()        # 缺少必填项会直接报错，启动即失败
```

**四个关键设计**：

| 设计 | 好处 |
| --- | --- |
| **类型注解** | `db_pool_size: int` 会从字符串 `"10"` 转成整数 |
| **必填项无默认值** | 缺少直接启动失败（**fail fast**） |
| **`Field(ge=, le=)`** | 防止配错（如 `pool_size=10000`） |
| **`extra="ignore"`** | 环境里有多余变量不影响 |

**`.env` 文件**：

```bash
APP_NAME=my-service
DEBUG=false
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
OPENAI_API_KEY=sk-xxxxx
JWT_SECRET=change-me-in-production
```

** `.env` 必须加到 `.gitignore`！**

```gitignore
.env
.env.local
*.key
```

**提供 `.env.example` 作为模板**（提交到 git，但不含真实值）：

```bash
# .env.example
APP_NAME=my-service
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
OPENAI_API_KEY=sk-your-key-here
JWT_SECRET=generate-a-random-string
```

> **这是行业标准做法**：新人 clone 后 `cp .env.example .env` 就能开始。

**关于 `fail fast` 的价值**：配置错误在**启动时**暴露，而不是在第一个用户请求时才崩 —— 差别巨大。

## 4.8 可观测性三支柱（面试常问）

| 支柱 | 是什么 | 回答什么问题 | 工具 |
| --- | --- | --- | --- |
| **Logs**（日志） | 离散事件的记录 | "**发生了什么**" | Loki / ELK |
| **Metrics**（指标） | 数值的时间序列 | "**系统健康吗**"（QPS、延迟、错误率） | Prometheus |
| **Traces**（链路追踪） | 一个请求在多个服务间的完整路径 | "**慢在哪一步**" | Jaeger / Tempo |

**一个具体的排查例子**：

```
① 告警响了: 错误率从 0.1% 涨到 5%        <- Metrics
② 看日志: 大量 "LLM API 超时"            <- Logs
③ 看 trace: 90% 的时间花在 LLM 调用      <- Traces
④ 结论: 是上游 LLM 服务变慢了，不是我们的 bug
```

**对这周的要求**：至少把 **Logs** 做扎实（结构化 + trace_id）。Metrics 和 Traces 在 Week4（监控）里展开。

## 4.9 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| pytest 找不到测试 | 文件名/函数名不符合 `test_*` | 按约定命名 |
| 测试互相影响 | fixture 用了模块级共享状态 | 用 `function` scope，或每测试重建 |
| 异步测试报 "coroutine never awaited" | 忘了 `asyncio_mode=auto` 或 `@pytest.mark.asyncio` | 配置好 |
| mock 没生效 | patch 的路径写错（要 patch **使用处**而非定义处） | 确认 import 路径 |
| `AsyncMock` 用了 `MagicMock` | 不能 await | 换 `AsyncMock` |
| mock 通过但线上失败 | mock 掩盖了真实行为差异 | 加少量真实集成测试 |
| 日志泄漏密码 | 没做字段过滤 | 加敏感字段黑名单 |
| 日志刷屏拖慢服务 | 循环里打 INFO | 降到 DEBUG 或只打汇总 |
| 生产环境看到一堆 DEBUG | 级别没配置 | 用环境变量控制级别 |
| `.env` 被提交到 git | 没加 `.gitignore` | 立即加入并从历史中移除 |

**关于 mock 路径最容易搞错的一点**：

```python
# mymodule.py
from httpx import AsyncClient          # ← 在 mymodule 里 import

async def fetch():
    async with AsyncClient() as c:     # ← 用的是 mymodule 命名空间里的 AsyncClient
        ...

# ✗ 错：patch 定义处
monkeypatch.setattr("httpx.AsyncClient", FakeClient)

# ✓ 对：patch 使用处（mymodule 的命名空间）
monkeypatch.setattr("mymodule.AsyncClient", FakeClient)
```

**记忆**：**patch 你代码里"看到"的那个名字。**
