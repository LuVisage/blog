## 4.2 为什么 LLM 应用必须流式

**先看用户体验的差距**：

```
【同步返回】
  用户点"发送"
     ↓
  [等待 15 秒 …… 界面完全没反应]
     ↓
  一次性显示 500 字的回答
  ↑ 用户在第 3 秒就会以为卡死了，可能直接刷新页面

【流式返回】
  用户点"发送"
     ↓
  0.3 秒后："今"
  0.35 秒后："今天"
  0.4 秒后："今天天气"
  ... 逐字出现
  ↑ 用户看到"正在思考"，愿意等待
```

**关键数字**（实测自案例代码）：

| 指标 | 数值 |
| --- | --- |
| **首字节延迟** | **6 ms** |
| 完整回答耗时 | 344 ms |

**首字节延迟是关键体验指标**。同步模式下用户要等 344ms 才看到任何东西；流式模式下 6ms 就有反馈。

**对长回答，差距更大**：

| 回答长度 | 同步等待 | 流式首字节 |
| --- | --- | --- |
| 100 字 | 0.5 秒 | 0.01 秒 |
| 1000 字 | 5 秒 | 0.01 秒 |
| 5000 字 | 25 秒 | 0.01 秒 |

> **另一个重要原因**：LLM 本身就是**逐 token 生成**的（Week16 Day5 讲过自回归）。
> 同步返回等于把已经生成好的 token 攒在服务端，白白浪费了"已经可以给用户看"的信息。

## 4.3 三种推送技术对比

| | 短轮询 | **SSE** | WebSocket |
| --- | --- | --- | --- |
| 方向 | 客户端拉 | **服务端→客户端（单向）** | **双向** |
| 协议 | HTTP | **HTTP（`text/event-stream`）** | WebSocket（需协议升级） |
| 自动重连 | —— | **浏览器内置** | 自己实现 |
| 实现复杂度 | 最低 | **低** | 高 |
| 穿过代理/防火墙 | 容易 | **容易**（就是 HTTP） | 可能被拦 |
| 适合 | 低频状态查询 | **LLM 流式输出、通知、日志** | 聊天室、协作编辑、游戏 |

**为什么 LLM 场景 SSE 就够了**：

```
LLM 的输出方向是【单向】的:
  客户端发一次 prompt -> 服务端持续推 token
  中间不需要客户端再发数据

单向 + 基于 HTTP + 自动重连 -> SSE 是最优解
```

**什么时候需要 WebSocket**：

- 用户要在生成过程中**打断**（需要双向）；
- 实时协作（多人同时编辑）；
- 游戏（高频双向）。

> **面试常问**：「LLM 流式输出你用 SSE 还是 WebSocket？为什么？」
>
> 答：SSE。因为 LLM 输出是单向的（服务端→客户端），SSE 基于 HTTP 更容易穿过代理、有内置重连，实现也更简单。只有需要"生成中途打断"这类双向交互时才考虑 WebSocket。

## 4.4 SSE 的报文格式

**SSE 极其简单 —— 就是纯文本，用特定格式**：

```
data: {"type":"start","trace_id":"abc123"}

data: {"type":"token","content":"今","index":0}

data: {"type":"token","content":"天","index":1}

data: {"type":"end","index":2}

```

**三条规则**：

| 规则 | 说明 |
| --- | --- |
| 每行以 `data: ` 开头 | 这是 SSE 规定的前缀 |
| **每条消息以两个换行结束** | `\n\n` 是消息分隔符 |
| Content-Type 必须是 `text/event-stream` | 否则浏览器不会按 SSE 解析 |

**其他可选字段**：

| 字段 | 作用 |
| --- | --- |
| `event: name` | 自定义事件类型（前端用 `addEventListener` 监听） |
| `id: 123` | 消息 ID，重连时浏览器会带 `Last-Event-ID` 头 |
| `retry: 3000` | 告诉浏览器重连间隔（毫秒） |
| `: comment` | 注释（心跳用，前端会忽略） |

**为什么用 `data: {json}\n\n` 而不是直接发文本**：

```python
# ✗ 直接发文本：如果内容里含 \n\n，会被误认为是消息边界
yield f"data: {text}\n\n"

# ✓ 发 JSON：换行被转义成 \n，不会破坏报文格式
yield f"data: {json.dumps({'content': text})}\n\n"
```

> **这是一个实际的坑**：LLM 的输出经常包含换行（尤其代码块），直接用文本会在客户端被拆成多条消息。

## 4.5 FastAPI 实现

```python
from fastapi.responses import StreamingResponse

@chat.post("/stream", summary="SSE 流式对话")
async def chat_stream(req: ChatRequest, llm: LLM, user: CurrentUser,
                      request: Request) -> StreamingResponse:
    trace_id = getattr(request.state, "trace_id", None)

    async def event_generator():
        idx = 0
        try:
            yield _sse(StreamChunk(type="start", trace_id=trace_id))       # ①

            async for token in llm.stream(req):                            # ②
                if await request.is_disconnected():                        # ③
                    logger.info("客户端断开，停止生成")
                    break
                yield _sse(StreamChunk(type="token", content=token, index=idx))
                idx += 1

            yield _sse(StreamChunk(type="end", index=idx))                 # ④
        except Exception as e:
            logger.exception("流式生成出错")
            yield _sse(StreamChunk(type="error", content=str(e)))          # ⑤

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",       # ★ 关键：关掉 Nginx 缓冲
        },
    )

def _sse(chunk: StreamChunk) -> str:
    return f"data: {chunk.model_dump_json()}\n\n"
```

**五个设计要点**：

| # | 要点 | 为什么 |
| --- | --- | --- |
| ① | **先发 start 事件** | 前端知道连接建立了，可以切换 UI 状态 |
| ② | **`async for` 逐块产出** | 依赖 Week1 Day3 的异步基础 |
| ③ | **检查 `is_disconnected()`** | 用户关页面后停止生成 —— **LLM 调用很贵** |
| ④ | **发 end 事件** | 前端知道回答完成（区别于"连接断了"） |
| ⑤ | **异常只能作为 error 事件发** | 流已经开始，**HTTP 状态码已经发出去了，改不了** |

**关于第 ⑤ 点（重要）**：

```python
# 流开始后，响应头已经发出，你无法再改状态码
# ✗ 这样不行
async def gen():
    raise HTTPException(500, "出错了")     # 客户端收到的是 200 + 半个响应

# ✓ 正确：把错误作为数据发出去，前端根据 type 处理
async def gen():
    try:
        ...
    except Exception as e:
        yield _sse(StreamChunk(type="error", content=str(e)))
```

> **这解释了为什么 SSE 接口的"错误处理"要在协议层面做**，而不是靠 HTTP 状态码。

## 4.6 客户端接入（前端三行代码）

```javascript
// 用 fetch + ReadableStream（推荐，能带 Authorization 头）
const resp = await fetch('/api/v1/chat/stream', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${token}`,
  },
  body: JSON.stringify({ prompt: '你好' }),
});

const reader = resp.body.getReader();
const decoder = new TextDecoder();
let buffer = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  buffer += decoder.decode(value, { stream: true });
  const lines = buffer.split('\n\n');
  buffer = lines.pop();                     // 最后一段可能不完整，留到下次

  for (const line of lines) {
    if (!line.startsWith('data: ')) continue;
    const ev = JSON.parse(line.slice(6));
    if (ev.type === 'token') appendText(ev.content);
    if (ev.type === 'end')   finish();
    if (ev.type === 'error') showError(ev.content);
  }
}
```

```javascript
// 用 EventSource（更简单，但【不能带自定义请求头】—— 不能传 Authorization）
const es = new EventSource(`/api/v1/chat/stream?prompt=${encodeURIComponent(p)}`);
es.onmessage = (e) => { /* ... */ };
es.onerror = () => es.close();
```

> **实战选择**：**用 `fetch` + `ReadableStream`**，而不是 `EventSource`。
>
> 因为 `EventSource` 只支持 GET，且**不能传 `Authorization` 头** —— 你只能把 token 放 URL 里（会进日志，不安全）。
> 而 `fetch` 可以自由设置请求头，还能用 POST。

## 4.7 客户端断连处理

**必须先回答一个问题**：为什么要在意客户端断开？

```
用户点了"发送"，等了两秒，觉得慢，关掉页面
     ↓
如果不检查断连:
  服务端继续生成完整回答 -> 调用 LLM -> 【花了钱】-> 结果没人看
     ↓
后果:
  · 白花 API 费用
  · 白占计算资源（可能拖慢其他用户）
  · 并发上限被无效请求占用
```

**实现**：

```python
async def event_generator():
    async for token in llm.stream(req):
        if await request.is_disconnected():
            logger.info("客户端断开，停止生成", extra={"user_id": user.id})
            break
        yield _sse(...)
```

**检查的时机很重要**：

| 做法 | 评价 |
| --- | --- |
| 每个 token 都检查 | 及时，但有微小开销 |
| 每 N 个 token 检查 | 折中方案 |
| 只在开始检查 | 意义不大 |

**注意**：`is_disconnected()` 的检测依赖底层连接的关闭通知。**如果中间有缓冲代理，可能延迟较久**（代理认为连接还开着）。

## 4.8 部署时的缓冲坑（最容易踩）

**这是流式输出最经典的坑。**

```
现象: 本地跑得好好的，部署到服务器后变成"攒完一次性返回"

原因: 中间的反向代理在缓冲

  客户端 <-> Nginx <-> 你的服务

  Nginx 默认会缓冲上游响应，直到攒够一定大小（proxy_buffer_size）
  或上游结束才发给客户端 —— 流式就被破坏了
```

**三层都要检查**：

### ① 应用层

```python
headers={"X-Accel-Buffering": "no"}
```

`X-Accel-Buffering` 是给 Nginx 看的私有头，告诉它别缓冲。**只对 Nginx 有效**。

### ② Nginx 配置（Week4 会讲）

```nginx
location /api/ {
    proxy_pass http://api:8000;
    proxy_buffering off;                  # ★ 关掉响应缓冲
    proxy_cache off;
    proxy_read_timeout 300s;              # 长连接要放宽超时
    proxy_set_header Connection '';       # 保持长连接
    chunked_transfer_encoding on;
}
```

### ③ 客户端 / 中间件

| 层 | 检查项 |
| --- | --- |
| CDN | 有些 CDN 会缓冲，需要单独配置 |
| 云负载均衡 | 如 AWS ALB 支持流式，但要注意空闲超时 |
| 客户端 | 用 `fetch` 的 `body.getReader()`，**不要用 `await resp.text()`**（那会等完整响应） |

**案例代码的测试专门验证了这一点**：

```python
def test_stream_tokens_are_incremental(client, auth_headers) -> None:
    """验证是【逐块】返回，而不是攒完一次性返回

    ★ 这个测试能抓住"以为在流式，其实是缓冲"的 bug ——
      在 Nginx 后面部署时最容易踩。
    """
    with client.stream("POST", "/api/v1/chat/stream", ...) as r:
        token_count = 0
        for line in r.iter_lines():
            if line.startswith("data: "):
                if json.loads(line[6:])["type"] == "token":
                    token_count += 1
        assert token_count > 5, f"只收到 {token_count} 个 token 事件"
```

**实测的首字节延迟**（案例代码真实运行）：

```
Content-Type: text/event-stream; charset=utf-8
X-Trace-Id:   66eb2f0702ca
X-Accel-Buffering: no
收到的 token: 回答：关于「流式输出测试」，我的看法是……
-> 共 21 个 token 事件
-> 首个事件延迟 6ms，全程 344ms
```

**6ms vs 344ms —— 这就是流式的价值。**

## 4.9 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 所有 token 同时到达 | 中间有代理缓冲 | `X-Accel-Buffering: no` + Nginx `proxy_buffering off` |
| 内容里的换行把消息拆散 | 直接发原始文本 | 发 JSON（换行被转义） |
| 客户端拿不到 Authorization | 用了 `EventSource` | 改用 `fetch` + `ReadableStream` |
| 流开始后返回 500 但客户端收到 200 | HTTP 状态码已发出 | 用 error 事件传递错误 |
| 用户关页面后还在烧钱 | 没检查断连 | `await request.is_disconnected()` |
| 长时间无输出被断开 | 空闲超时 | 发心跳注释 `: ping\n\n` |
| 客户端 `await resp.text()` 卡住 | 那会等完整响应 | 用 `body.getReader()` 流式读 |
| 用 `async for` 但没生效 | 底层不是异步生成器 | 确认 `llm.stream()` 是 `async def` + `yield` |
| 限流中间件把流截断 | 中间件包装了 response | 让流式路由豁免 |

**关于心跳**：如果 LLM 首 token 延迟很长（如 10 秒），中间设备可能认为连接空闲而断开。可以定期发注释：

```python
async def event_generator():
    yield ": ping\n\n"        # 注释行，前端会忽略
    ...
```

## 4.11 一句话总结

**SSE 就是"用 HTTP 持续推送文本"：`data: <json>\n\n` 是全部格式，`StreamingResponse` 是全部实现；它比 WebSocket 更适合 LLM 场景（单向、基于 HTTP、自动重连），但必须在应用层加 `X-Accel-Buffering: no`、在 Nginx 层关 `proxy_buffering`，否则你写的流式会被中间件攒成一次性返回 —— 而且这个坑只在部署后才暴露。**
