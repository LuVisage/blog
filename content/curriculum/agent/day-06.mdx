## 6.1 模型的致命缺陷：知识截止 + 幻觉

大模型训练完成后，知识就**冻结**在训练数据里了。两个后果：

1. **不知道新东西**：训练截止后的新闻、你的公司文档、你电脑里的文件，它一概不知；
2. **一本正经地胡说（幻觉）**：被问到自己不知道的事，它会自信地编造——因为它的任务就是"生成像样的文字"，而不是"承认不知道"。

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是当前最主流的解法，思路朴素得惊人：

> **回答问题前，先查资料，再把资料连同问题一起交给模型。**

就像开卷考试：模型答题（生成 Generation），但允许它先翻书（检索 Retrieval），答案由书里的内容**增强（Augmented）**。

## 6.2 RAG 三环节全景图（本周的作战地图）

```
【① 索引 Indexing】离线准备，每天/每周跑一次
  你的文档（PDF/MD/TXT...）
      │ 切分 Chunking：长文切成小段
      ▼
  一段段文本块
      │ Embedding：每段变成向量（一串数字）
      ▼
  向量库 Milvus（存"文本 + 向量"）

【② 检索 Retrieval】用户提问时实时跑
  用户问题 → Embedding → 问题向量
      │ 在 Milvus 里找"距离最近"的 k 个文本块
      ▼
  Top-k 相关文本块

【③ 生成 Generation】实时跑
  系统提示词："根据以下资料回答，资料里没有就说不知道"
  + 资料（检索到的文本块）
  + 用户问题
      │ 交给 LLM
      ▼
  有依据的回答
```

## 6.3 Embedding：把文字变成"坐标"

向量检索的前提是**机器能算两段文字有多像**。怎么算？把文字映射成**向量**（一长串数字，如 768 个 float），语义相近的文字，向量在空间中**离得近**：

```
"苹果手机怎么样"  → [0.12, -0.34, 0.87, ...]   ┐
"iPhone 好用吗"   → [0.10, -0.31, 0.85, ...]   ┘ 语义近 → 向量近
"今天下雨了吗"    → [-0.71, 0.42, -0.09, ...]  → 语义远 → 向量远
```

干这件事的模型叫 **Embedding 模型**（嵌入模型）。注意它和 LLM 是**两个不同的模型**：

| | LLM（对话模型） | Embedding 模型 |
|---|---|---|
| 输入 | 一段话 | 一段话 |
| 输出 | 一段话（token 流） | **一串数字**（固定长度向量） |
| 用途 | 聊天、推理、生成 | 算"像不像" |
| 本教程配置 | `.env` 的 `LLM_*` | `.env` 的 `EMBEDDING_*`（Ollama nomic-embed-text） |

### 调用 Embedding（LangChain 版）

```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(
    model="nomic-embed-text",
    base_url="http://localhost:11434/v1",   # Ollama 也兼容 OpenAI 接口
    api_key="ollama",
    check_embedding_ctx_length=False,       # ★ 非 OpenAI 官方服务必须关掉！
)

vec = embeddings.embed_query("苹果手机怎么样")      # 单个问题 → 向量
print(len(vec))                                     # 768（维度数，模型决定）
print(vec[:5])                                      # 前 5 个数字
```

> **`check_embedding_ctx_length=False` 是什么？** 该参数默认 True，会用 tiktoken 把文本转成 token 编号再发请求——这是给 OpenAI 官方 API 的特权。Ollama/DeepSeek 等兼容服务只收原始文本，会报 `invalid input type`。**接非 OpenAI 官方 embedding 服务时，一律加上这个参数**（本教程全部案例已加）。

- `embed_query(text)`：给"查询问题"生成向量（检索时用）；
- `embed_documents([...])`：给一批"文档块"生成向量（入库时用，**比逐个调用快很多**）。

## 6.4 相似度：余弦相似度（亲手算一遍！）

向量有了，怎么算"离得近"？最常用的是**余弦相似度（cosine similarity）**：两个向量的夹角越小越相似。公式（高中向量知识，别怕）：

```
cos(θ) = (A · B) / (|A| × |B|)
        A·B = 对应位置相乘再求和（点积）
        |A|  = sqrt(各元素平方和)（模长）
```

结果范围 [-1, 1]，**越接近 1 越相似**。手写实现：

```python
import math

def cosine_similarity(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))                       # 点积
    norm_a = math.sqrt(sum(x * x for x in a))                    # |A|
    norm_b = math.sqrt(sum(x * x for x in b))                    # |B|
    return dot / (norm_a * norm_b)

v1 = embeddings.embed_query("苹果手机怎么样")
v2 = embeddings.embed_query("iPhone 好用吗")
v3 = embeddings.embed_query("今天下雨了吗")
print(cosine_similarity(v1, v2))    # 期望 0.7+
print(cosine_similarity(v1, v3))    # 期望远低于上一行
```

> **今天的"顿悟时刻"**：所谓"向量检索"，数学上就是**暴力/近似地找与问题向量余弦相似度最高的 k 个文档向量**。Milvus 的底层就是干这件事的引擎（它还做了索引加速，亿万级数据毫秒级出结果）。

## 6.5 Chunking：为什么要把长文档切碎

两个原因：

1. **Embedding 模型吃不下长文**：nomic-embed-text 等模型有最大输入长度（如 8192 token），整本《三体》塞不进去；
2. **精度**：一段 5000 字的文章 embedding 成一条向量，主题被"平均"掉了，检索时很难精准命中。切成 300~500 字的小块，每块主题集中，命中率高。

### 切分器：RecursiveCharacterTextSplitter

LangChain 最常用的切分器，**按优先级逐级切**：先按段落（`\n\n`）→ 不行按换行（`\n`）→ 再按句号 → 最后按字符。这样切出来的块**尽量完整地包住句子和段落**。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=300,        # 每块最多 300 个字符
    chunk_overlap=50,      # 相邻两块重叠 50 字符（防止关键句被切断）
    separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""],
)

chunks = splitter.split_text(long_text)
```

**`chunk_overlap` 是新手最容易忽略的关键参数**：切分可能正好把一个知识点拦腰截断（"……今天要讲的是 RAG" / "的原理，非常重要"）。前后块重叠 10%~20%，关键句至少完整出现在一块里。

> 参数怎么调？没有银弹，取决于文档类型：技术文档 300~800 字符、法律条文 500~1000、对话记录 200~400。**第 14-15 天的评估环节就是用来科学地调这些参数的。**

### `day06_embedding.py` —— 向量与相似度全体验

```python
"""Day 6 案例 1：Embedding 调用 + 余弦相似度手算"""
import os, math
from pathlib import Path
from dotenv import load_dotenv
load_dotenv(Path(__file__).resolve().parents[2] / ".env")

from langchain_openai import OpenAIEmbeddings

# 从 .env 读取 embedding 配置（Ollama 免费方案 / 云端均可）
embeddings = OpenAIEmbeddings(
    model=os.environ["EMBEDDING_MODEL"],
    base_url=os.environ["EMBEDDING_BASE_URL"],
    api_key=os.environ["EMBEDDING_API_KEY"],
)

def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(x * x for x in b))
    return dot / (norm_a * norm_b)

# 三个句子：前两个语义相近
s1 = "苹果手机怎么样"
s2 = "iPhone 好用吗"
s3 = "今天下雨了吗"

v1, v2, v3 = (embeddings.embed_query(s) for s in (s1, s2, s3))

print(f"向量维度：{len(v1)}")
print(f"向量前 5 位：{[round(x, 4) for x in v1[:5]]}")
print(f"\n'{s1}' vs '{s2}' 相似度：{cosine_similarity(v1, v2):.4f}   ← 应该较高")
print(f"'{s1}' vs '{s3}' 相似度：{cosine_similarity(v1, v3):.4f}   ← 应该较低")

# embed_documents 批量接口（入库专用，比循环 embed_query 快）
docs_vec = embeddings.embed_documents(["第一段文字", "第二段文字", "第三段文字"])
print(f"\n批量嵌入 {len(docs_vec)} 个文档，每个维度 {len(docs_vec[0])}")
```

**要点**：两行相似度对比就是"向量检索"的雏形。记住数字的相对关系比绝对大小重要——不同 embedding 模型的分数分布不同。

### `day06_chunking.py` —— 切分参数体感实验

```python
"""Day 6 案例 2：文本切分 —— chunk_size / overlap 体感实验"""
from langchain_text_splitters import RecursiveCharacterTextSplitter

sample = """第一章 向量数据库
向量数据库是专门为高维向量检索设计的数据库系统。它能够存储海量的向量数据，
并通过近似最近邻搜索算法，在毫秒级时间内返回与查询向量最相似的 Top-K 结果。
Milvus 是目前最流行的开源向量数据库之一，支持十亿级向量的毫秒检索。

第二章 RAG 的流程
RAG 的流程分为三个环节：索引、检索、生成。索引环节将文档切分成块并向量化入库；
检索环节根据用户问题召回相关块；生成环节由大模型基于召回内容组织答案。"""

def show(name, chunks):
    print(f"\n【{name}】共 {len(chunks)} 块：")
    for i, c in enumerate(chunks, 1):
        print(f"  块{i}（{len(c)}字）：{c[:30]}...")

# ① 不重叠：块与块之间可能有信息被切断
splitter1 = RecursiveCharacterTextSplitter(chunk_size=100, chunk_overlap=0)
show("chunk=100 无重叠", splitter1.split_text(sample))

# ② 带重叠：关键句在相邻块中重复出现，保证不被切断
splitter2 = RecursiveCharacterTextSplitter(
    chunk_size=100, chunk_overlap=30,
    separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""],
)
show("chunk=100 重叠30", splitter2.split_text(sample))

# ③ 大块：块少但每块主题可能混杂
splitter3 = RecursiveCharacterTextSplitter(chunk_size=250, chunk_overlap=30)
show("chunk=250 重叠30", splitter3.split_text(sample))
```

**要点**：跑完对比三种输出——① 可能把"近似最近邻搜索"切成两半；② 重叠后关键内容至少完整出现在一块；③ 大块块数少、检索快但精度低。**这三个旋钮（chunk_size / overlap / separators）你将在 Day 13 系统调优。**
