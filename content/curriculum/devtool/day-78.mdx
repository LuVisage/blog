## 一、为什么需要链路追踪

微服务下一个请求经过多个服务，出问题时：

- 日志分散在各服务，无法串起来；
- 「慢」到底慢在哪个服务、哪次数据库调用？

**链路追踪**把一次请求的所有环节串成一条 Trace，可视化每个 Span 的耗时。

## 二、核心概念

| 概念 | 说明 |
| --- | --- |
| Trace | 一次完整请求的调用链（Trace ID 全局唯一） |
| Span | 链中的一环（一次 RPC / DB 查询 / 函数），有耗时与父子关系 |
| Parent Span | 上游调用者 |
| Context Propagation | 跨服务透传 Trace ID（HTTP header `traceparent` / `uber-trace-id`） |
| Sampling | 采样（全量会爆炸，通常 1-10%） |

## 三、Jaeger vs Zipkin

| 维度 | Jaeger | Zipkin |
| --- | --- | --- |
| 出身 | Uber → CNCF 毕业项目 | Twitter，最早的开源追踪系统 |
| 存储 | ES / Cassandra / Badger | ES / MySQL / Cassandra / 内存 |
| 功能 | 更丰富（服务依赖图、对比、深链路分析） | 简洁，够用 |
| 采样 | 自适应采样 | 基础采样 |
| UI | 现代、功能全 | 简洁 |
| 生态 | OpenTelemetry 一等公民 | 被 OTel 支持 |
| 现状 | 活跃（v2 基于 OTel Collector） | 维护模式 |

**建议**：新项目直接用 **OpenTelemetry 采集 + Jaeger 或云厂商后端**；Zipkin 适合轻量快速验证。

## 五、接入示例（基于 OpenTelemetry）

### Node.js

```ts
import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';

const sdk = new NodeSDK({
  serviceName: 'order-service',
  traceExporter: new OTLPTraceExporter({
    url: 'http://localhost:4318/v1/traces',     // 直接发 Jaeger
  }),
  instrumentations: [getNodeAutoInstrumentations()],
});

sdk.start();
```

启动：`node --import ./instrumentation.ts src/server.ts`

### Python

```python
# pip install opentelemetry-distro opentelemetry-exporter-otlp
# opentelemetry-bootstrap -a install
# opentelemetry-instrument --service_name order-api python app.py

from opentelemetry import trace
tracer = trace.get_tracer(__name__)

with tracer.start_as_current_span("process_payment") as span:
    span.set_attribute("payment.provider", "alipay")
    do_payment()
```

### Go

```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
)

func initTracer() func() {
    exporter, _ := otlptracehttp.New(context.Background(),
        otlptracehttp.WithEndpoint("localhost:4318"), otlptracehttp.WithInsecure())
    tp := sdktrace.NewTracerProvider(sdktrace.WithBatcher(exporter))
    otel.SetTracerProvider(tp)
    return func() { _ = tp.Shutdown(context.Background()) }
}
```

### HTTP 跨服务透传

OpenTelemetry 的自动埋点会自动注入与解析 `traceparent` 头，**前提是**：
- 服务间调用都走被埋点的 HTTP client；
- 网关/Nginx 不要剥离 `traceparent` 头（检查配置）。

手动透传示例：

```ts
import { propagation, context } from '@opentelemetry/api';

// 发送方
const headers: Record<string, string> = {};
propagation.inject(context.active(), headers);
await fetch('http://user-service/api/profile', { headers });

// 接收方（框架自动处理；手动时）
const ctx = propagation.extract(context.active(), req.headers);
```

```powershell

```

访问 http://localhost:9411 查看 UI。

### 上报数据

```powershell
# 方式一：OTel Collector 导出到 Zipkin

#   zipkin:

curl.exe -X POST http://localhost:9411/api/v2/spans `
  -H "Content-Type: application/json" `
  -d '[{"traceId":"a1b2c3d4e5f60718","id":"1122334455667788","name":"get /api/users","timestamp":1757800000000000,"duration":45000,"localEndpoint":{"serviceName":"api"}}]'
```

Python 直接接入：

```powershell
pip install pyzipkin
```

```python
from py_zipkin.zipkin import zipkin_span

def do_work():
    with zipkin_span(
        service_name='order-api',
        span_name='submit_order',
        transport_handler=lambda x: send_to_zipkin(x),  # 上报函数
        sample_rate=10.0,        # 10% 采样
    ):
        process()
```

## 七、Jaeger/Zipkin UI 使用

### 查询链路

1. 选 Service（如 `order-service`）；
2. 选 Operation（如 `POST /api/orders`）；
3. 设置时间范围与 Tags（如 `http.status_code=500`）；
4. 点 Find Traces。

### 分析

| 视图 | 用途 |
| --- | --- |
| Trace Timeline | 瀑布图，直观看每个 Span 耗时占比 |
| Span Details | 标签、日志、耗时明细 |
| Service Dependencies（Jaeger） | 服务依赖拓扑图 |
| Compare（Jaeger） | 对比两条链路差异 |
| Deep Link | 从日志中的 traceId 直接跳转 |

**典型排查**：

```
接口 P95 从 200ms 涨到 2s
  → 查慢 Trace
  → 看瀑布图：哪个 Span 占了大头
  → 若是 DB Span → 查那条 SQL（见数据库教程）
  → 若是下游 HTTP Span → 跳到下游服务的链路继续看
  → 若是自身计算 Span → 看代码逻辑
```

## 八、采样策略

| 策略 | 说明 |
| --- | --- |
| 头部采样 | 请求入口决定是否采样（简单，可能丢错误链路） |
| 尾部采样 | 收集完整链路后按规则决定（保留慢/错误链路，推荐） |
| 自适应采样 | 按流量动态调整（Jaeger 特性） |

OTel 环境变量：

```powershell
$env:OTEL_TRACES_SAMPLER="parentbased_traceidratio"
$env:OTEL_TRACES_SAMPLER_ARG="0.1"     # 10%
```

尾部采样在 Collector 中配置（`tail_sampling` processor）：

```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: random
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
```

## 九、与日志/指标联动

1. **日志 → Trace**：日志里带 `traceId`，Grafana/Loki 配 Derived field 跳转 Jaeger；
2. **指标 → Trace**：Prometheus Exemplars 标注样本对应 traceId；
3. **Trace → 日志**：Jaeger 中配置日志的跳转链接（按 traceId 搜 Loki）。

实现三者互跳后，排查路径变成：**告警（指标）→ 定位服务 → 看链路找瓶颈 → 查日志看细节**。

## 十、常见问题

| 问题 | 解决 |
| --- | --- |
| 只有单个 Span，链路断开 | `traceparent` 头未透传（网关剥离）；异步任务未传递 context |
| 服务名不显示 | `serviceName` 未配置或配置不一致 |
| 找不到某条 Trace | 采样未命中；调高采样率或用尾部采样保留错误 |
| Span 时间不准 | 各服务器时钟不同步（NTP 对时） |
| 数据量太大 | 降采样率、Collector 过滤低价值服务 |
| Jaeger 存储满 | 配 ES ILM 或用 Cassandra；设置 retention |
| 异步/消息队列链路断 | 需手动把 context 注入消息头并在消费端提取 |
