## 一、两者定位

| 维度 | Jira | Linear |
| --- | --- | --- |
| 定位 | 企业级项目与事务管理平台 | 现代、极快的研发协作工具 |
| 上手难度 | 高（配置灵活但复杂） | 低（开箱即用，Opinionated） |
| 速度 | 一般 | 极快（键盘优先） |
| 工作流定制 | 极强（任意状态机） | 相对固定（Backlog → Todo → In Progress → Done） |
| 报表 | 非常丰富（燃尽图、速度图、Epic 报告） | 精简但够用 |
| 集成 | 几乎所有工具（Atlassian 生态） | GitHub/GitLab/Slack 深度集成 |
| 适合 | 大企业、复杂流程、合规要求 | 中小研发团队、追求效率 |

## 二、Jira 使用

### 核心概念

| 概念 | 说明 |
| --- | --- |
| Project | 项目（Scrum / Kanban 模板） |
| Issue | 工作项（Story / Task / Bug / Epic / Sub-task） |
| Epic | 大需求（含多个 Story） |
| Sprint | 迭代（通常 2 周） |
| Board | 看板（Backlog / 进行中 / 完成） |
| Workflow | 状态流转规则 |
| Story Points | 工作量估算（斐波那契 1/2/3/5/8/13） |

### 典型使用流程

```
1. 需求池（Backlog）：产品把需求都建为 Story
   - 标题：用户能通过手机号登录
   - 描述：As a ... I want ... So that ...
   - 验收标准（Acceptance Criteria）：条目化，可测试
2. 计划会议（Planning）：
   - 拆子任务（Sub-task）
   - 估点（Story Points）
   - 拖入 Sprint
3. Sprint 执行：
   - 每日站会过一遍 Board
   - 状态流转：To Do → In Progress → In Review → Done
   - 阻塞项打 Flag（红旗）
4. 完成（Review + 回顾）：
   - 演示 Sprint 成果
   - 看燃尽图与速度
   - 回顾会记录改进项
```

### 实用功能

| 功能 | 用途 |
| --- | --- |
| JQL 搜索 | 高级查询：`project = APP AND status != Done AND assignee = currentUser()` |
| 自动化 | `When issue moved to Done → close linked PR` |
| 仪表盘 | 自定义 Gadget（燃尽图、饼图、待办列表） |
| 过滤器 | 保存常用查询（我的待办、本周到期） |
| 关联 | "blocks" / "is blocked by" / "relates to" |
| 时间跟踪 | 登记工时（如公司要求） |
| 集成 | GitHub/GitLab（提交信息带 issue key 自动关联） |

### JQL 示例

```
# 我的未完成任务
assignee = currentUser() AND status != Done

# 本 Sprint 的 Bug
sprint in openSprints() AND issuetype = Bug

# 超过 3 天没动的
status = "In Progress" AND updated < -3d

# 高优且未排期
priority in (Highest, High) AND sprint is EMPTY
```

提交信息关联：`git commit -m "APP-123 修复登录超时"` → Jira 自动关联该 issue。

## 三、Linear 使用

### 特点

- **Cmd+K 万能命令**：创建、搜索、跳转全部键盘完成；
- 自动同步 Git 分支与 PR（创建分支时代入 issue ID）；
- Cycles（周期，类似 Sprint）、Projects、Roadmap 一应俱全；
- 界面极快，几乎没有加载感。

### 核心概念

| Linear | 对应 Jira |
| --- | --- |
| Issue | Issue |
| Project | Epic |
| Cycle | Sprint |
| Team | Project（团队维度） |
| Roadmap | 跨季度规划 |

### 使用流程

```
1. 建 Issue（Cmd+K → "New issue"）
   - Title、Description、Label、Assignee、Estimate（点数）
   - 关联 Project 与 Cycle
2. 用 GitHub 集成：从 issue 一键创建分支（自动命名 xxx-123-title）
3. PR 打开后自动把 issue 移到 "In Progress"，合并后自动 "Done"
4. Cycle 视图看进度；Roadmap 看季度规划
```

### 好用功能

- **Triage**：新 issue 先进入待分诊队列，再分配；
- **Templates**：Bug 报告模板自动带复现步骤结构；
- **Insights**：团队速度、周期时间趋势；
- **Slack 集成**：在频道里建 issue、更新状态；
- **移动端**：体验完整。

## 四、流程方法论（工具无关）

### Scrum vs Kanban

| 维度 | Scrum | Kanban |
| --- | --- | --- |
| 节奏 | 固定迭代（1-4 周） | 持续流动 |
| 角色 | PO / SM / 团队 | 无强制角色 |
| 变更 | 迭代内尽量不变 | 随时可增删 |
| 度量 | 速度图、燃尽图 | 周期时间、WIP |
| 适合 | 需求相对稳定的产品团队 | 运维、支持、需求多变的团队 |

### 好任务的写法

```
标题：用户能通过手机号 + 验证码登录
描述：
  背景：目前仅支持邮箱登录，移动端用户转化低
  范围：登录页改造 + 短信服务对接 + 验证码校验
  验收标准：
    1. 输入合法手机号后 60 秒内收到验证码
    2. 验证码 5 分钟有效，错误 3 次锁定 10 分钟
    3. 登录成功后跳转来源页
  技术备注：
    - 接口定义见 OpenAPI 文档 /auth/sms-login
    - 需新增限流规则（短信接口）
```

要点：**可验证的验收标准**，避免「完成但不符合预期」的扯皮。

## 五、与代码平台联动

| 平台 | 联动方式 |
| --- | --- |
| GitHub | 提交/PR 提到 issue key 自动关联；Linear/Jira 有官方 GitHub App |
| GitLab | MR 标题或描述带 key；配置集成 |
| Slack/飞书 | 建 issue、状态变化通知 |
| CI | 流水线失败自动创建 Bug issue（可配自动化） |

## 六、常见问题

| 问题 | 解决 |
| --- | --- |
| Jira 太慢 | 减少自定义字段、精简工作流、减少看板 Gadget |
| 状态流转混乱 | 明确每个状态的进入/退出标准（DoR / DoD） |
| 估点不准 | 用历史速度校准；点数大就拆任务 |
| 任务积压不关 | 定期清理（Grooming）；设 "stale" 规则自动提醒 |
| Linear 迁移数据 | 官方支持 Jira 导入（含历史） |
| 团队不用工具 | 从「任务看板」开始，先解决可见性问题，再谈流程 |

## 七、最佳实践

1. **工具服务于流程**，不要照搬大厂复杂流程到小团队；
2. **一个团队一套工具**，别 Jira 记需求 + 飞书表格记进度；
3. **Issue 粒度 1-3 天**完成，超出的拆分；
4. **验收标准必写**，且可测试；
5. **自动化例行公事**：状态流转、提醒、关联（Jira Automation / Linear 内置自动）；
6. **回顾要落地**：每次回顾挑 1-2 项改进行动，下个迭代验收。
