> 安装与钩子基础用法见 [../01-版本控制/06-提交钩子.md](/learn/devtool/day-06)。
> 本篇聚焦**在代码质量链路中如何组合使用**。

## 一、三者的分工

```
git commit
   │
   ├─► Husky        负责「触发」：把脚本挂到 Git 钩子上
   │
   ├─► lint-staged  负责「范围」：只对本次改动的文件跑命令
   │
   └─► commitlint   负责「门禁」：校验提交信息是否符合规范
```

为什么需要 lint-staged：全量 ESLint 可能跑 1 分钟，只检查改动文件通常 1-2 秒，**提交体验是关键**。

## 二、完整落地配置（pnpm 项目）

### 1. 安装

```powershell
pnpm add -D husky lint-staged @commitlint/cli @commitlint/config-conventional
npx husky init
```

### 2. package.json

```json
{
  "scripts": {
    "prepare": "husky",
    "lint": "eslint . --max-warnings 0",
    "format:check": "prettier . --check",
    "typecheck": "tsc --noEmit"
  },
  "lint-staged": {
    "*.{js,jsx,ts,tsx,vue}": ["eslint --fix --max-warnings 0", "prettier --write"],
    "*.{css,scss,md,json,yml,yaml}": ["prettier --write"]
  }
}
```

### 3. `.husky/pre-commit`

```sh
pnpm lint-staged
```

### 4. `.husky/commit-msg`

```sh
pnpm exec commitlint --edit "$1"
```

### 5. `commitlint.config.js`

```js
export default {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [2, 'always', [
      'feat', 'fix', 'docs', 'style', 'refactor', 'perf',
      'test', 'build', 'ci', 'chore', 'revert',
    ]],
    'subject-case': [0],
    'header-max-length': [2, 'always', 100],
  },
};
```

提交信息格式：

```
<type>(<scope>): <subject>

[optional body]
[optional footer]
```

示例：`feat(auth): 新增手机号登录`、`fix(cart): 修复数量为 0 时价格异常`

## 三、推荐的门禁分层

| 阶段 | 检查内容 | 耗时目标 | 工具 |
| --- | --- | --- | --- |
| 保存文件 | 格式化 | 立即 | 编辑器 format on save |
| pre-commit | 改动文件 lint + format | &lt; 5 秒 | lint-staged |
| commit-msg | 提交信息规范 | &lt; 1 秒 | commitlint |
| pre-push | 类型检查 + 单测 | &lt; 60 秒 | tsc --noEmit、vitest run |
| CI | 全量 lint + 测试 + 构建 | 不限 | GitHub Actions 等 |

原则：**越靠前越快，越靠后越严**。

## 四、pre-push 示例

`.husky/pre-push`：

```sh
pnpm typecheck && pnpm test -- --run
```

只跑受影响的测试（Vitest）：

```sh
pnpm vitest related --run $(git diff --name-only origin/main...HEAD -- '*.ts' '*.tsx')
```

## 五、Python 项目的等价方案

同一思路用 `pre-commit` 框架（见 [../01-版本控制/06-提交钩子.md](/learn/devtool/day-06)）：

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: https://github.com/commitizen-tools/commitizen
    rev: v3.27.0
    hooks:
      - id: commitizen
```

## 六、常见问题

| 问题 | 解决 |
| --- | --- |
| 克隆后钩子不生效 | 钩子在 `.git/hooks`（不进版本库），克隆后需 `pnpm install`（触发 `prepare`）或手动 `npx husky` |
| lint-staged 改了文件但没重新 add | lint-staged 会自动把修复后的文件重新暂存，无需手动操作 |
| CI 里跑 husky 失败 | CI 设 `HUSKY=0`，钩子只管本地 |
| 提交被阻塞影响紧急发布 | `git commit --no-verify` 临时跳过（团队约定只在紧急时用） |
| Windows 钩子报错 | `.husky/*` 文件保证 LF 换行：`.gitattributes` 加 `*.sh text eol=lf` |
| commitlint 校验 `$1` 变量为空 \vert 用 `pnpm exec commitlint --edit "$1"`（shell 形式），确保换行符正确 |
| monorepo 中 lint-staged 找不到配置 | 各包独立配置 lint-staged，或在根目录用 `lint-staged --cwd` 分发 |

## 七、最佳实践

1. **钩子只做快速检查**；类型检查、单测放 pre-push 或 CI。
2. **规则单一来源**：lint 配置只有一份（ESLint/Biome/Ruff），钩子与 CI 调用同一命令。
3. **失效兜底**：CI 必须重复跑相同检查，钩子可被 `--no-verify` 绕过，不可作为唯一防线。
4. **渐进式**：老项目先把 lint-staged 设为 `warn`，清理完存量再升 `error`。
