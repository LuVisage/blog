## 一、Kafka 篇

### 核心概念

| 概念 | 说明 |
| --- | --- |
| Broker | Kafka 服务节点 |
| Topic | 消息主题（逻辑分类） |
| Partition | 分区（并行单元，同分区内有序） |
| Offset | 消息在分区内的位置 |
| Consumer Group | 消费组（组内分区独占，实现并行消费） |
| Replication | 副本（`replication-factor` 决定容错） |

### 命令行工具（kafka-topics / kafka-console-*）

```bash
# 列出 Topic
kafka-topics.sh --bootstrap-server localhost:9092 --list

# 创建 Topic（3 分区、2 副本）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 2

# 查看 Topic 详情
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# 扩容分区（不可减少）
kafka-topics.sh --bootstrap-server localhost:9092 --alter --topic orders --partitions 6

# 删除 Topic
kafka-topics.sh --bootstrap-server localhost:9092 --delete --topic orders

# 生产消息
kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
> {"orderId":1,"amount":99}

# 消费消息（从最早开始）
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic orders --from-beginning --max-messages 10

# 消费组信息（确认积压）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --list
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group order-service
# 关注 LAG 列（积压量），持续增长说明消费跟不上

# 重置 offset（谨慎，会重复消费或跳过）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group order-service --topic orders --reset-offsets --to-earliest --execute
```

### Kafka Tool / Offset Explorer

**Offset Explorer（原 Kafka Tool）** 是常用图形客户端：

1. 下载：https://www.kafkatool.com/download.html
2. 配置连接：`File → Add New Connection` → 填 Bootstrap Servers、版本、认证（SASL/SSL）；
3. 常用功能：

| 功能 | 位置 |
| --- | --- |
| 查看 Topic 列表与分区 | Topics 树 |
| 查看分区消息 | 双击 Topic → Partitions → Data |
| 按 offset 跳转 | Data 面板输入 offset |
| 过滤消息（正则/JSON） | Data 面板 Filter |
| 发送消息 | 右键 Topic → Produce Message |
| 查看消费组积压 | Consumers 树 |
| 按 Key 搜索消息 | Data 面板搜索 |
| 修改/新建 Topic | 右键 → Create/Alter Topic |
| 导出消息 | 选中消息 → Save |

**使用场景**：排查「消息有没有发出去」「消费为什么积压」「消息内容对不对」。

### 常见问题排查

```
消息没收到？
  ├─ Producer 发成功了吗？→ kafka-console-consumer 或 Offset Explorer 看主题里有没有
  ├─ 分区选对了吗？      → key 决定分区，检查分区器逻辑
  ├─ 消费组 offset 落后？→ kafka-consumer-groups --describe 看 LAG
  ├─ 消费报错静默吞掉？  → 检查消费端日志与死信队列
  └─ 重复消费？          → 检查是否手动提交 offset、rebalance 频繁
```

| 问题 | 解决 |
| --- | --- |
| 消费积压（LAG 大） | 加消费者实例（不超过分区数）、优化消费逻辑、增加分区 |
| 频繁 rebalance | 调大 `max.poll.interval.ms`、减少单次 poll 条数 |
| 消息重复 | 业务做幂等（唯一键 + upsert）；开启事务或幂等 producer |
| 消息丢失 | acks=all + 副本数 ≥ 3 + min.insync.replicas ≥ 2；消费端先处理再提交 offset |
| 顺序错乱 | 同一业务 key 路由到同一分区（用 key 分区） |

## 二、RabbitMQ 篇

### 核心概念

| 概念 | 说明 |
| --- | --- |
| Producer / Consumer | 生产者 / 消费者 |
| Exchange | 交换机（routing 规则） |
| Queue | 队列（消息存储） |
| Binding | 交换机与队列的绑定规则 |
| Routing Key | 路由键 |
| vhost | 虚拟主机（隔离环境） |

四种 Exchange 类型：

| 类型 | 路由规则 |
| --- | --- |
| direct | routing key 完全匹配 |
| fanout | 广播到所有绑定队列 |
| topic | 通配符匹配（`*` 一个词，`#` 多个词） |
| headers | 按 header 匹配（少用） |

### 管理台（Management UI）

启用插件：

```bash
rabbitmq-plugins enable rabbitmq_management
# Docker
docker run -d --name rabbit -p 5672:5672 -p 15672:15672 rabbitmq:3-management
```

访问 http://localhost:15672（默认 guest/guest，仅限本机；生产必须新建用户）。

| 页面 | 用途 |
| --- | --- |
| Overview | 消息速率、连接、队列总数 |
| Connections | 查看连接与客户端信息 |
| Channels | 信道状态 |
| Queues | 队列列表、**Ready/Unacked 数量**、手动发消息/取消息 |
| Exchanges | 交换机与绑定关系 |
| Admin | 用户、权限、vhost、策略 |
| Policies | 设置 TTL、镜像、死信策略 |

### 排查要点

- **Ready 堆积**：没有消费者或消费太慢；
- **Unacked 堆积**：消费者拿到了但没 ack（处理慢/卡死/异常未 ack）；
- 点击队列 → Get messages 手动取一条查看内容；
- `Publish message` 手动发测试消息；
- Admin → Policies 设置：

| 策略 | 作用 |
| --- | --- |
| `x-message-ttl` | 消息过期时间 |
| `x-max-length` | 队列最大长度（超出丢弃或拒绝） |
| `x-dead-letter-exchange` | 死信交换机（失败消息转存） |
| `ha-mode: all` | 镜像队列（高可用，经典队列） |

### 命令行管理（rabbitmqadmin）

```bash
rabbitmqadmin list queues name messages consumers
rabbitmqadmin list connections
rabbitmqadmin get queue=orders count=5
rabbitmqadmin purge queue=orders              # 清空队列（危险）
rabbitmqadmin declare queue name=test durable=true
rabbitmqadmin publish exchange=amq.default routing_key=orders payload='{"a":1}'
```

或直接调用 HTTP API：

```bash
curl -u admin:pass http://localhost:15672/api/queues | jq '.[] | {name, messages, consumers}'
```

### 常见问题

| 问题 | 解决 |
| --- | --- |
| 队列消息只增不减 | 检查消费者是否在线/报错；查看 Unacked 是否卡住 |
| 消息丢失 | 队列/消息持久化（durable + delivery_mode=2）+ publisher confirms |
| 重复消费 | 消费端幂等；ack 在业务成功后执行 |
| 内存告警阻塞生产者 | 加消费者、设置 TTL/最大长度、开启 lazy queues |
| 死信堆积 | 检查死信队列（DLQ），分析失败原因后重投 |
| guest 无法远程登录 | 创建新用户并赋权限（guest 默认仅 localhost） |

## 三、Kafka vs RabbitMQ 选型

| 维度 | Kafka | RabbitMQ |
| --- | --- | --- |
| 模型 | 分布式日志（拉模型） | 消息代理（推模型） |
| 吞吐 | 极高（百万级/秒） | 高（万级/秒） |
| 延迟 | 毫秒-十毫秒 | 微秒-毫秒 |
| 消息顺序 | 分区内有序 | 队列内有序 |
| 消息保留 | 按时间/大小保留（可重复消费） | 消费后删除（ack 后） |
| 复杂路由 | 弱（靠 Topic 设计） | 强（多种 Exchange） |
| 典型场景 | 日志、埋点、流处理、大数据管道 | 业务解耦、任务队列、RPC |
| 运维复杂度 | 高（需 ZooKeeper/KRaft） | 中 |

**结论**：数据管道/高吞吐 → Kafka；业务消息/复杂路由/低延迟 → RabbitMQ。
